# 保証台帳スキルの設計

## 目的と背景

保証台帳（guarantee ledger）は、壊してはいけない約束を人間が読める一枚の文書に宣言し、その約束を裏付けるテストへの索引を張る仕組みである。manako で 2026-08-13 から試作し、26 保証が稼働している。

本設計の目的は 2 つある。

1. manako 固有の設計文書に閉じている運用ルールを、**再現可能なスキル**として `agent-toolkit` へ移す。
2. 保証の**出自ルール**を導入する。台帳へ載せる根拠を「実装とテストに存在すること」から「指示・判断の出来事に遡れること」へ変更する。

2 は試作からの方針転換であり、既存 26 保証の処遇を伴う。

## 方針転換: 出自ルール

### 変更内容

保証は、指示・判断の出来事へ遡れるものだけを載せる。実装とテストが存在しても、遡れなければ載せない。実装が指示の隙間を埋めた振る舞いは、正しく動いていても保証ではない。

### 変更理由

実装から保証を拾うと、エージェントが指示されずに決めた振る舞いが契約へ昇格する。後にその振る舞いが誤りだと判明しても、台帳が誤りを守る側へ回る。これは「literal 実行は指示の誤りをそのまま実装し、テストごと固定してしまう」という既知の失敗の、台帳版である。

試作時の事後棚卸しは、この危険を 2 方向で実証している。

| 失敗の向き | 実測 |
|---|---|
| 拾えない | 「約束したいがテストが無い」振る舞いは台帳へ載せず Action へ積む規則が既に存在した。化石化していない意図には手が届かない |
| 拾いすぎる | G-005 はテストが存在し保証に見えたが、pin 確認により pro / business の上限が守られていないと判明した（部分的な空手形） |

事後棚卸しが復元できるのは、過去の判断がテストへ化石化した分までである。規範の新規宣言はやりとり（レビュー・設計判断）からしか来ない。

### 昇格経路

指示されていない中間の振る舞いを保証したくなった場合、観測は昇格させない。裁定が昇格させる。

1. まず判断の出来事を作る（レビューで裁定する / 設計文書へ決定として書く）
2. その文書を出自として台帳へ載せる

manako にはこの原型が 2 つ実在する。G-031 は R1 レビューの裁定に由来し、G-006 は PR #1314 の rubric に由来する。

## 正本の配置

| 対象 | 置き場所 | 状態 |
|---|---|---|
| 汎用ルール（責務分割・書式・ID 体系・判定基準・索引形式・出自・突合・rubric） | `agent-toolkit/skills/guarantee-ledger/SKILL.md` | 新・正本 |
| pin 確認の手順 | `agent-toolkit/skills/guarantee-pin-check/SKILL.md` | 新・正本（現在どこにも手順書が存在しない） |
| manako `.docs/plans/2026-08-13-guarantee-ledger-design.md` | manako | 歴史記録＋固有束縛へ降格 |
| manako `scripts/check-guarantees.sh` ほか、`pre-pr.md` Check 4 | manako | 固有配線として残置 |
| standards | — | 変更しない。昇格条件をスキルへ 1 節書く |

### standards を触らない理由

manako の設計文書は「試作の是非が判明する前に共通契約へ加えない」として standards 変更を明示的に保留した。本設計はその保留を解除しない。スキル化は道具の整備であり、共通契約への昇格ではない。

**昇格の条件は本設計では定めない。** 出自ルールはまだ 1 度も運用されておらず、条件を今書けば推測がルールへ化ける。昇格の可否は効果判定の後に別途判断する。

`agent-toolkit` の CLAUDE.md は「standards がルールを持ち、agent-toolkit は道具を持つ。ルールの中身を複製しない」と定めるが、これは standards に既存のルールを複製することを禁じる規定である。standards に存在しない手順ルールをスキルが正本として持つ先例は `delegation-spec` にある（standards に委任仕様の規定は無く、standards にある収束規律だけを参照している）。

## スキル分割

起動タイミングで分割する。概念で分割しない。

### `guarantee-ledger`（コア）

| 節 | 内容 |
|---|---|
| ① | 目的と責務分割。面ごとの「形の正本」と台帳の関係。形の正本が無い面の分岐。出自ルールと復元の天井 |
| ② | 6 列の表書式、面ごとのセクション |
| ③ | ID 体系（`G-###`・欠番を再利用しない・retired 記法・並行採番の繰り下げ） |
| ④ | 載せる / 載せないの二段の門 |
| ⑤ | テスト索引形式（`file::describe [> it]`・変動値を書かない・1 索引で足りないなら保証を分割） |
| ⑥ | 必須フィールドと空手形禁止。テスト不在の振る舞いは Action へ |
| ⑦ | pin 確認の意味と限界。実施手順は `guarantee-pin-check` へのポインタ |
| ⑧ | 導入手順 |
| ⑨ | checker の移植限界 |
| ⑩ | 段階 2 エージェント突合（未実行であることを明記） |
| ⑪ | 効果判定 rubric |
| ⑫ | `decision-test-chain` との境界 |

### `guarantee-pin-check`

pin 未確認の保証をまとめて潰すキャンペーン時に起動する。手順は Step A〜D。

| Step | 内容 |
|---|---|
| A | 裏付けテストを読まずに（test-blind）、保証文と実装だけから mutant を設計する |
| B | mutant を適用し、裏付けテストが赤くなることを確認する |
| C | 復元し、`git diff` が空であることを確認する |
| D | 台帳の `pin確認` 欄へ `YYYY-MM-DD <壊し方の散文>` を記入する |

必須要素:

- **mutant の作者 ≠ 実装の作者。** 実装を書いた agent 以外の人間、または fresh context の独立 agent が実施する
- 実施順の設計時に、裏付け索引の**包含関係**を確認する。先行する保証の索引が後続保証の裏付けを含む場合、後続の Step A をテスト未読の別主体が代行する
- 部分的な空手形（mutant の一部が緑のまま）は `pin確認` を空欄のまま残し、Action へ積む
- 委任は `delegation-spec` に従う

この手順は manako の 1 回のキャンペーン（2026-08-14、G-001〜G-006）の実施記録から復元したものであり、出自は n=1 である。スキル本文にその旨を明記する。

### スキル化しないもの

| 対象 | 理由 |
|---|---|
| 台帳 → 検証仕様書の変換 | 実行回数 2 件で書式が未確定。共通化は 3 回目から |
| 段階 2 エージェント突合 | 一度も実行されていない。コアスキルの 1 節に留める |
| `decision-test-chain` | 合否判定が Action として持ち越し中。判定前にスキル化しない |

## 適用範囲

外部から観測できる面全般（HTTP API・CLI 出力・スケジューラ・Webhook・画面）を対象とする。

### 「形の正本」の一般化

試作時のルールは `docs/openapi.yaml` という具体的な文書名に依存していた。これを次へ一般化する。

> その面にインターフェース定義があるなら、それが形の正本である。台帳はそれを読んでも分からない振る舞いだけを持つ。

形の正本が存在しない面（バッチ処理など）では、載せる / 載せないの線が消えて台帳が何でも入る箱になる。この場合は次のいずれかを選ぶ。

1. 先に形の正本を作る
2. その面を台帳の対象外とする

### 判定基準を発明しない

載せる / 載せないの原則（条件分岐・網羅性・副作用・エラー語彙の安定性・存在秘匿・迷ったら載せない）だけを一般化し、CLI や画面に固有の判定基準は書かない。一度も実行されていない面の基準を正本へ焼き込むと、推測がルールへ化ける。manako の API 判定表は実証済みの worked example として残す。

## 表書式

5 列から 6 列へ変更する。

| 列 | 内容 |
|---|---|
| `ID` | 保証を一意に識別する連番 `G-###` |
| `保証` | 壊してはいけない観測可能な振る舞い |
| `対応実装` | 保証を担う実装ファイル。リポジトリルートからの相対パス。複数は `, ` 区切り |
| `裏付けテスト` | 保証を実証するテストへの索引 |
| `pin確認` | 保証を壊して裏付けテストが赤くなることを観測した証跡。空欄、または `YYYY-MM-DD <壊し方の散文>` |
| `出自` | **新設。** 保証の根拠となる指示・判断の出来事。`<リポジトリルートからの相対パス>::<見出し>` |

### 面のセクション

面ごとにセクションを分ける。**保証が生まれてからセクションを作る。** 空のセクションを先に置かない。

試作時は「棚卸し済み（保証 0 件）。」という記法で未棚卸しとの区別を保っていたが、この記法は事後棚卸しを前提としている。出自ルールの下では棚卸しを行わないため、記法ごと廃止する。保証 0 件の面は、セクションが存在しないことで表現される。

### 出自列の仕様

形式は `<path>::<見出し>` の一形式とする。PR やレビューでの裁定も、まず `.docs/reviews/` か `.docs/plans/` へ書いてから参照する。これにより「観測は昇格させない、裁定が昇格させる」が機構として働き、文書に残らないやりとりは保証にできない。

`decision-test-chain` の注釈と同じアドレス体系になる（あちらはテスト → 見出し、こちらは台帳 → 見出し。同じ判別線を逆向きに引いた実装）。

制約:

- `::` は**最初の 1 つ**で分割する。見出しに `::` が含まれても壊れない
- 見出しに `|` を含むものは表セルを壊すため使えない

### 列の追加位置

**末尾へ追加する。** 実測により、末尾追加なら既存の checker 2 本は無改修で動作する。

```
sed 's/|$/| 出自 |/' .docs/guarantees.md > <tmp>
LEDGER=<tmp> bash scripts/check-guarantees.sh
  → checked=26 broken=0 unpinned=1   （元と同一、exit 0）
```

`check-guarantees.sh` は `awk -F'|' '{print $4}'` 等の位置指定で読み、`check-guarantee-cochange.sh` は `IFS='|' read -r _ id _ implementation _ _` で読む。後者は最後の変数へ残り全部が入るため、7 列目が増えても `implementation` は `$4` のまま変わらない（別途検証済み）。

## 機械検査の境界

判定の基準を次のとおり定める。

> 機械はポインタの健全性を検査する。意味は人間が検査する。テストは pin が検査する。

### checker への追加

| 検査 | 内容 |
|---|---|
| 出自が空 | `BROKEN` |
| 出自パスのファイル実在 | `BROKEN`。`対応実装` 列に対する既存ロジックの再利用 |

### 意図的に実装しない検査

| 検査 | 実装しない理由 |
|---|---|
| 見出しの実在検査 | 形式を検査しているのに意味を検査したつもりになる。もっともらしい見出しを指していれば通るため、確信を製造する。todoke の `decision-chain.ts` による「嘘の注釈の検出」は 0 件だが、嘘が無かったのか検出できないのかを区別できない。見出しの妥当性はレビューと段階 2 突合が担う |
| 参照先が git 追跡済みかの検査 | 追跡外の問題は todoke 時代のものであり manako では解消済み（`.docs/plans` は 123 ファイルが追跡済みと実測）。ファイル実在検査で実務上足りる |
| 主張範囲（「12 endpoint」等）の被覆検査 | 台帳の主張とテストの被覆のズレは検出できない。これは既知の盲点として ⑨ へ記載する |

## 同梱物と移植限界

`skills/guarantee-ledger/scripts/` へ `check-guarantees.sh` と `check-guarantee-cochange.sh` を雛形として同梱する。導入時にプロジェクトへコピーし、`LEDGER` / `TEST_DIR` / `BASE_REF` を合わせる。

スキルへ明記し、解決はしない限界:

- vitest 形式の `describe` / `it` / `test` 宣言をパースする前提
- テスト索引のファイル名部分にサブディレクトリを含められない（`*/*` は `BROKEN`）
- ID は `G-` + 3 桁固定
- `describe` と `it` の所属関係は解析しない。同一ファイル内に独立に存在すれば通る
- テストの中身が保証を実証しているかは検査しない（pin 確認の担当）

exit code 契約:

| コード | 扱い |
|---|---|
| 0 | 続行 |
| 2（cochange のみ） | `WARN`。PR をブロックしない |
| それ以外の非 0 | `FAIL`。修正するまで PR を作らない |

## 導入手順（⑧の内容）

1. checker 2 本をプロジェクトへコピーし、`LEDGER` / `TEST_DIR` / `BASE_REF` を合わせる
2. 台帳を**空で開始する**。または指示の情報源（`.docs/plans` の決定・PR rubric・レビュー裁定・risk-registry）から起こす
3. プロジェクトの `CLAUDE.md` / `AGENTS.md` へ追記トリガーを 1 行加える
4. `/pre-pr` 等の PR 前チェックへ checker を配線し、exit code 契約を明記する

**実装とテストを掃いて保証を起こす手順（初回棚卸し）は行わない。** 試作時はこの手順で 26 保証を起こしたが、出自ルールの導入により禁止する。台帳が空であることは「まだ何も約束していない」という正しい状態を表す。

## manako 側の変更

### 既存 26 件の再裁定

出自を必須にすると既存 26 件は全て `BROKEN` になる。事後棚卸しで作られたため、定義上どれも出自を持たない。

遡及付与は「実装から拾った保証へ後付けで出自をでっち上げる」作業になりかねない。それは本方針転換が防ごうとしているものを別ルートで再現する。したがって作業の形は「出自を探す」ではなく「**今ここで裁定し直す**」とする。

手順:

1. 再裁定文書を 1 本起こす
2. 各行を次のいずれかへ振り分けた一覧を作る
   - 元の裁定が実在するもの（G-031 → R1 レビュー、G-006 → PR #1314 の rubric を `.docs/reviews/` へ転記）はそれを指す
   - 元の裁定が無いが保証として維持するものは、再裁定文書の該当節を指す
   - 維持しないものは `(retired: YYYY-MM-DD 出自不明・再宣言せず)` とする
3. 人間が行ごとに keep / retire を決める
4. PR をマージする。**このマージが判断の出来事になる**

ハードルール:

- **日付を遡らせない。** 遡及付与した出自は遡及した日付を持つ
- **keep / retire を worker や司令塔が単独で決めない。** 出自へ遡れないテナント分離保証を黙って落とさず、keep / retire の一覧として人間の前へ出す

### その他の変更

| 対象 | 変更 |
|---|---|
| `.docs/plans/2026-08-13-guarantee-ledger-design.md` | 冒頭へ正本移設の宣言を追加。本文は歴史記録として保持 |
| `.docs/guarantees.md` | 6 列へ移行し、26 行へ出自を付与（再裁定の結果を反映） |
| `scripts/check-guarantees.sh` | 出自の空検査とファイル実在検査を追加 |
| `AGENTS.md` の追記トリガー行 | スキルへの参照を追加 |
| `claude-code-plugin/commands/pre-pr.md` Check 4 | 変更しない |

**順序制約: checker への「空 = BROKEN」の追加と 26 行の出自付与は同一 PR で行う。** 分けると、その間 checker が赤くなる。

- **台帳 → 検証仕様書の変換（残り 24 件）。** 出自ルール適用後に残る行は指示された約束であり、それを検証することは当初の意図（保証台帳に書いてあることを検証する）そのものである。スキル完成後の最初の実戦とする
