# dev-process プラグイン設計書

## 概要

個人開発プロジェクトに「AI時代の開発プロセス設計書」のパターンを再現可能な形で導入するClaude Codeプラグイン。

### 解決する課題

- 新しいプロジェクトを始めるたびに、開発プロセスの基盤(テンプレート、規約、CI)を手動で構築している
- 仕様(docs/specs/)とコードの同期が人依存で形骸化しやすい
- プロセスの遵守状況を定期的にチェックする仕組みがない

### 設計方針

| 方針 | 説明 |
|------|------|
| 依存ゼロ | 他プラグインに依存しない。gh CLIのみツールとして利用 |
| CLAUDE.mdがランタイム | 日常のIssue/PR作成は生成されたCLAUDE.mdの規約でClaude Codeが自然に従う |
| デフォルト内蔵 + オーバーライド | テンプレートはプラグインに同梱。プロジェクト側で上書き可能 |
| Actions に機械的チェックを委譲 | スキルはAIでしかできないこと(文脈理解、仕様生成、品質判断)に集中 |
| 段階的導入 | setup → spec-sync → process-audit の順で育てる |

### 責務分離: スキル vs GitHub Actions

| 担当 | 内容 |
|------|------|
| **GitHub Actions(機械的)** | `closes #XX` 存在チェック、コミットメッセージlint、frontmatterスキーマ検証、テンプレートセクション充足、リンク切れ検出、draft放置検出、放置Issue検出 |
| **スキル(AI判断)** | CLAUDE.md生成、docs/specs作成・更新、仕様-コード乖離検出、GitHub Actionsワークフロー生成、プロセス健全性監査 |

## スキル1: setup

### 役割

新規/既存プロジェクトにdev-processの全基盤を導入する。

### トリガー

"dev-processを導入して" "開発プロセスをセットアップして" "プロジェクトにプロセス基盤を入れて"

### ワークフロー

```
1. プロジェクト分析
   ├── 言語/フレームワーク検出
   ├── 既存CLAUDE.md検出
   ├── 既存テンプレート検出
   └── docs/specs/ の有無

2. 差分検出 & 生成計画
   ├── 何が足りないか一覧化
   ├── 何が古いか検出
   └── ユーザーに生成計画を提示 → 承認

3. 生成(承認後)
   ├── CLAUDE.md に開発規約セクションを追記/更新
   ├── .github/ISSUE_TEMPLATE/specification.yml
   ├── .github/PULL_REQUEST_TEMPLATE.md
   ├── .github/workflows/pr-check.yml
   ├── .github/workflows/weekly-check.yml
   ├── docs/specs/ ディレクトリ + README
   └── gh label create (ラベル体系)

4. 検証
   └── 生成物の一覧と確認事項をユーザーに提示
```

### テンプレートオーバーライド

```
優先順位:
1. .dev-process/templates/<file>   ← プロジェクト固有(あれば優先)
2. プラグイン内 generators/<file>  ← デフォルト
```

### CLAUDE.md 生成ルール

- 既存CLAUDE.mdがある場合: `# Dev Process Rules` セクションのみ追記/更新
- 既存CLAUDE.mdがない場合: 新規作成
- 生成する規約セクションの内容:

```markdown
# Dev Process Rules (Generated by dev-process plugin)

## Issue ルール
- テンプレートに従い作成
- 受け入れ条件は検証可能な形式で記述
- type / area ラベルを付与

## コミットメッセージ規約
- Conventional Commits準拠
- format: <type>(<scope>): <subject>
- scope: 英語kebab-case (機能領域)
- subject: 日本語で簡潔に
- body: 「なぜこの実装方法を選んだか」を日本語で
- footer: refs #XX または closes #XX 必須

## PR ルール
- closes #XX 必須
- 受け入れ条件充足チェックリスト
- 仕様からの変更点セクション(なければ「なし」と明記)
- docs/specs更新有無の明示
- コード変更 + 仕様更新 + テスト を常にセットで含める

## docs/specs ルール
- 「何がどうなっているか」を記述する
- 「なぜそうなっているか」はPR/Issueに残す
- frontmatter必須 (type, title, area, tags, doc_status, created, updated)
- コードに影響する仕様変更はPRにセットで含める

## 言語使い分け
- frontmatterフィールド名、area値、tags値、ファイル名、ラベル: 英語
- 本文、コミットsubject/body、Issue/PR description: 日本語
```

### 生成物一覧

| 生成物 | 配置先 | 内容 |
|--------|--------|------|
| 開発規約 | CLAUDE.md (セクション追記) | コミット規約、Issue/PR/docs/specsルール |
| Issueテンプレート | .github/ISSUE_TEMPLATE/specification.yml | 概要、背景、受け入れ条件、影響範囲 |
| PRテンプレート | .github/PULL_REQUEST_TEMPLATE.md | closes、変更概要、受け入れ条件充足、仕様変更点、docs更新 |
| PR品質ゲート | .github/workflows/pr-check.yml | closes必須、コミットlint、frontmatter検証 |
| 週次チェック | .github/workflows/weekly-check.yml | リンク切れ、draft放置、放置Issue |
| ラベル | GitHub Labels (gh CLI) | type:*, priority:*, status:*, area:* |
| docs構造 | docs/specs/README.md | ディレクトリ説明と運用ルール |

## スキル2: spec-sync

### 役割

docs/specsの作成・更新・乖離検出。AIの文脈理解が必要な仕様管理を担う。

### トリガー

"仕様を書き起こして" "仕様を更新して" "乖離チェックして" "spec-syncを実行して"

### 3つの呼び出しパターン

#### A. 初回生成

```
1. コードベースを分析
2. 機能領域(area)を洗い出し
3. 各areaのdraftを生成(frontmatter付き)
4. ユーザー確認 → docs/specs/ に配置
```

#### B. PR連動更新

```
1. git diff から変更内容を把握
2. 影響するdocs/specs/ファイルを特定
3. 該当ファイルの更新案を提示
4. ユーザー確認 → 更新
```

#### C. 乖離検出

```
1. docs/specs/ を全件読み込み
2. 各仕様の記述とコード実態を比較
3. 乖離箇所をレポート
4. 修正提案(仕様側 or コード側)
```

### frontmatter スキーマ

```yaml
---
type: feature | api | data-model | screen | batch | integration
title: "日本語タイトル"
area: job-management        # 英語kebab-case
tags: [api, authentication]  # 英語kebab-case
doc_status: draft | stable | deprecated
created: 2026-03-09
updated: 2026-03-09
related:
  - docs/specs/xxx.md
  - "#123"
---
```

### 記述方針

- 仕様には **「何がどうなっているか」** を記述する
- **「なぜそうなっているか」** はPR/Issue/commitに残す
- この分離により、仕様は現状の事実として信頼でき、変更理由は追跡チェーンで辿れる

## スキル3: process-audit

### 役割

プロセス全体の健全性を監査するメタチェック。

### トリガー

"プロセスの健全性を確認して" "開発プロセスを監査して" "process-auditを実行して"

### チェック項目

#### 1. インフラ健全性

- CLAUDE.md に Dev Process Rules セクションがあるか
- Issue/PR テンプレートが存在するか
- GitHub Actions ワークフローが存在し有効か
- ラベル体系が揃っているか
- 不足があれば "setup を再実行してください" と案内

#### 2. トレーサビリティ監査

- 直近N件のPRに closes #XX があるか
- 直近N件のコミットにIssue参照があるか
- 追跡チェーンの断裂箇所を報告

#### 3. 仕様カバレッジ

- コードの機能領域 vs docs/specs/ のarea一覧
- カバーされていない領域を検出
- doc_status: draft が長期放置されていないか
- deprecated ファイルの棚卸し

### レポート形式

```markdown
# Dev Process Audit Report

## Summary
| カテゴリ | スコア | 備考 |
|---------|--------|------|
| インフラ | A | 全て揃っている |
| トレーサビリティ | B | PR 2件で closes 欠落 |
| 仕様カバレッジ | C | 3領域が未文書化 |

## 要対応
- [ ] PR #45 に closes #XX を追記
- [ ] area: notification の仕様を新規作成
- [ ] docs/specs/auth.md の doc_status: draft を確認

## 推奨アクション
1. spec-sync で未文書化領域のドラフトを生成
2. ...
```

## 既存プラグインとの関係

| 既存プラグイン | dev-process | 関係性 |
|---------------|-------------|--------|
| github:create-issue | 不要 | CLAUDE.md規約 + Issueテンプレートで代替 |
| github:create-pr | 不要 | CLAUDE.md規約 + PRテンプレートで代替 |
| spec:spec-coordinator | 不要 | spec-syncが自前で仕様生成・更新を担う |

dev-processプラグインは他プラグインを参照せず、単体で完結する。

## 設計書との対応

| 設計書の章 | 対応するスキル/生成物 |
|-----------|---------------------|
| 1章 設計思想 | 全スキル共通の原則 |

| 3章 要望管理(Notion) | スコープ外(将来拡張) |
| 4章 開発フロー(GitHub) | setup (テンプレート、ラベル、CLAUDE.md規約) |
| 5章 仕様と実装の同期 | spec-sync |
| 6章 品質ゲート | setup (Actions生成) |
| 7章 CLAUDE.md | setup (CLAUDE.md生成) |
| 8章 運用開始ステップ | setup → spec-sync → process-audit の段階導入 |
| 9章 リスクと対策 | process-audit (形骸化検出) |

### スコープ外(将来拡張候補)

- Notion連携(要望管理フロー)
- Slack連携(起票UI)
- Starlight連携(仕様閲覧サイト)
- GitHub Projects連携(ビュー構成)

## 使用頻度と運用イメージ

| スキル | 頻度 | タイミング |
|--------|------|-----------|
| setup | プロジェクト開始時、設計書更新時 | 1回 + 必要時 |
| spec-sync | PR作成前後、定期 | 週1-2回 |
| process-audit | マイルストーン、スプリント振り返り | 月1-2回 |
