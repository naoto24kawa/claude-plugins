# guarantee-interview スキル設計

保証台帳へ「判断の出来事」を供給する裁定インタビューの設計。`guarantee-ledger` / `guarantee-pin-check` に次ぐ3本目のスキルとして新設する。

## 1. 背景 — 欠けているのは観測ではなく裁定

`guarantee-ledger` は**出自ルール**（保証は指示・判断の出来事へ遡れるものだけを載せる）を持ち、事後棚卸し（実装とテストを読んで保証を起こす手順）を禁じている。この規律は、エージェントが指示されずに決めた振る舞いが契約へ昇格するのを防ぐ。

一方でこの規律は、既存アプリに対しては台帳を薄いまま固定する。既存アプリの振る舞いの大半は出自を持たないため、載せられる行が構造的に増えない。

SKILL.md ④ はこの状況への答えを既に持っている。

> 観測は昇格させない。裁定が昇格させる。中間の振る舞いを保証したければ、まず判断の出来事を作る（レビューで裁定する / 設計文書へ決定として書く）。それから台帳へ載せる。

しかし「判断の出来事を作る」手順は存在しない。本設計はその手順を埋める。

### 3段のうち、実在するのは両端だけである

| 段 | 担当 | 状態 |
|---|---|---|
| 観測 | `guarantee-ledger` ⑩ 段階2突合 | **実在**。2026-08-17 に manako で初回実行済み |
| 裁定 | （不在） | **本設計の対象** |
| 宣言 | `guarantee-ledger` ①〜⑨ + checker | 実在 |

⑩ の初回実行（`manako/.docs/reviews/2026-08-17-guarantee-stage2-audit.md`）は `unrequested` を 11 件検出した。うち裁定されたのは `2026-08-17-guarantee-audit-adjudication.md` の 3 件（U-1 / U-6 / G-027 の partial）のみで、**残り 10 件（`unrequested` 9 件、および G-010 の partial 1 件）は台帳にも risk-registry にも Action にも入らず、レポートの中だけに存在する**。

裁定の 3 件はいずれもエージェントが実装・スキーマ・設計文書を調査して判断したものである。件2 では `notificationLogs.incidentId` の NOT NULL 制約まで掘って「構造的に他の選択肢がない」ことを確認している。人間に一問すれば答えが出ることに、長大な考古学を要している。**裁定のスループットがボトルネックである。**

## 2. 解く問題

1. 既存アプリで、出自を持たない実在の振る舞いを、捏造せずに保証へ昇格させる経路がない
2. ⑩ が検出した `unrequested` の行き先が定義されていない（10 件が宙吊り）
3. 裁定が高コストで、人間の意図を引き出す経路がない

## 3. 位置づけと境界

```
⑩ 突合 ──観測──▶ guarantee-interview ──裁定──▶ 台帳
（実装を読む）        （人間に聞く）           （宣言する）
```

### 事後棚卸しとの違い

本機構は「実装から保証を起こす」ように見えるため、禁止された事後棚卸しの復活かという問いに必ず晒される。答えを設計の芯に置く。

> 観測は実装から来てよい。**昇格は今ここでの人間の裁定から来る。**

これは manako の出自ルール移行（`2026-08-17-guarantee-reprovenance.md`）が既に引いた線と同一である。同文書は「出自を**探す**作業ではなく、各行について**今ここで裁定し直す**作業である」と規定し、遡及付与を禁じた。本機構も同じく、過去の判断を捏造せず、現在の判断を新しく作る。

事後棚卸しが禁じられる理由は「実装が決めた振る舞いが、人間の判断を経ずに契約へ昇格する」ことであり、人間の裁定を経る経路はその理由に抵触しない。

### 崩壊モード

本機構の失敗形は**ラバースタンプ**である。「これは意図どおりですね？」に yes を並べるだけの運用に落ちれば、出自の捏造装置となり、禁じたはずの事後棚卸しと同じものへ潰れる。以下の設計判断はすべてこの崩壊モードへの対策である。

## 4. 入口

入口は2つ持つが、いずれも「問いカード」へ正規化してから同一の裁定ループへ入る。

| 入口 | 種 | 使う場面 |
|---|---|---|
| A（先行） | ⑩ 突合の `unrequested` / `partial` | 台帳が既にある面。初回投入の材料が既に存在する |
| B | 面の walkthrough（仕様書・画面・形の正本を見ながら順に問う） | 台帳がゼロの面。⑩ を回す前のブートストラップ |

**新しいキューを作らない。** 入口 A のキューは突合レポートそのものである。入口 B は面の一覧がキューになる。

## 5. 問いの門 — 何を問いにするか

⑩ の初回実行が実地で使った3条件をそのまま採用する（`stage2-audit.md` §1）。

1. 台帳に無い
2. **形の正本（OpenAPI・CLI ヘルプ・型定義等）を読んでも分からない**
3. 利用者から観測でき、壊れたら困る

この門を通らないものは問いにしない。門は機械的・基準が明文であり、人間の判断を要さない。

## 6. 裁定ループ

### 提示は中立に行う

エージェントは「実装はこうなっている」という事実だけを提示し、**推奨を述べない**。「意図的に見える」「妥当と思われる」といった評価語を含めない。

問いカードに含めるもの:

- 観測した振る舞い（利用者から見た形で書く。内部実装の用語で書かない）
- その振る舞いが現れる操作・経路
- 形の正本（OpenAPI 等）がその点について何も言っていないことの確認結果
- 壊れた場合に利用者へ起きること

含めないもの: 実装がそうなっている理由の推測、他の選択肢の評価、エージェントの結論。**技術的必然性の調査（「スキーマ制約上その選択肢しかない」等）も、問う前には行わない。** 人間が ② を選んだ場合、その調査は不要になる。

### 選択肢は3つに固定する

| 選択 | 意味 | 行き先 |
|---|---|---|
| ① | 意図どおり | **台帳へ**（`pin確認` は空欄で入る） |
| ② | 意図していない | 修正 Action へ積む。**現行挙動を台帳に載せない** |
| ③ | 判断できない | 保留。次回へ持ち越す |

人間へ問うのは「**意図か否か**」だけである。「保証に値するか」は §5 の門が既に判定しており、裁定の場で再度問わない。

同じ判断を二度させる設計（①「約束だ」と②「意図だが約束ではない」を対等に並べる形）は採らない。人間が「約束と呼ぶほどでは」で流せる逃げ道を作ると、門を通った実害ある振る舞いが宙に消える。ラバースタンプの逆向きの失敗（取りこぼし）である。

### ② が生命線である

既存アプリの仕様再確認は、保証だけでなく**バグと仕様漏れも掘り出す**。エージェントが指示の隙間を埋めた振る舞いは、正しく動いていても正しいとは限らない。② を持たない機構は現状追認装置であり、誤った実装を契約へ昇格させる。

### ③ を正当な出口として置く

SKILL.md ①「迷ったら載せない」が既にこれを支持している。新ルールの発明ではなく既存原則の適用である。

### 理由の一文を必須とする

選択だけを記録すると、⑪ の形骸化 rubric にそのまま落ちる。人間の理由は**逐語で**残す。要約すると、後から読んだときに「エージェントが書いた理由」と区別できなくなる。

### 但し書き — 固定したくない場合

「意図どおりだが、近く変える／変える余地を残したい」場合は、① を選んだうえで台帳ではなく risk-registry へ回す。**この理由に限定する。**「約束と呼ぶほどでは」は理由として認めない。

実例は `audit-adjudication.md` 件2 である。「incident 削除時に notification log を実削除する」は意図的だが、台帳へ載せると将来 `incidentId` を nullable にして履歴保持へ改善する変更が保証違反になる。同文書はこれを「改善そのものを妨げる」として台帳へ追加しないと裁定した。

選択肢として対等に並べず、理由を限定した脱出口として置くのは、逃げ道化を防ぐためである。

## 7. 記録

裁定文書1本 `<repo>/.docs/reviews/YYYY-MM-DD-guarantee-interview-<面>.md` を作る。既存の `audit-adjudication.md` と同型とする。

- **1件 = 1節**とし、その節見出しがそのまま出自 `<path>::<見出し>` になる
- 順序を固定する: **会話 → 裁定文書へ記入 → 台帳へ反映**
- 人間の理由は逐語で残す

会話は揮発する。SKILL.md ②「文書に残らないやりとりは保証にできない」がそのまま効く。

## 8. 規模と打ち切り

1セッション **5〜10 件**を上限とする。打ち切り条件:

- 件数上限に達した
- 人間が止めた
- **③ が3連続した**（提示が悪いか人間が疲れている。いずれもその日の続行に意味がない）

裁定済み item を裁定文書へ記録し、次回は残りから再開する（冪等・再開可能）。キューは突合レポートであり消えない。

⑩ は「一致が多いことは打ち切りの理由にしない」（網羅性が価値）だが、本機構は逆に積極的に打ち切ってよい。1件ごとに独立した価値が出るため、途中で止めても成果が残る。

## 9. ⑪ 効果判定 rubric との衝突と改訂

`guarantee-ledger` SKILL.md ⑪ は現在こう規定する。

> 出自欄が「台帳更新のために作られただけの文書」を指すようになったら、形骸化と判定する。

**本機構は、まさに台帳更新のために文書を作る。** 字義どおり読むと本機構の産物はすべて形骸化判定になる。正しく動いた機構が違反として検出される rubric は、次の実施者に「基準へ合わせるための改悪」を迫るため、改訂する。

判別線を引き直す。

| | 形骸化 | 健全 |
|---|---|---|
| 文書が記録するもの | 台帳へ載せるという**手続き** | 人間が**実際にした判断** |
| 観測できる差 | ① ばかりが並ぶ | ② ③ が混ざる |

改訂後の判定基準:

> 裁定文書が記録しているのが手続きか判断かで見る。**② と ③ が一度も出ないセッションが続いたら、門か提示が壊れているサインとして扱う。**

「② ③ が N% 出ること」のような数値は焼き込まない。正当に ① ばかりの回もありうるうえ、変動する値を成功条件にすると次の実施者が基準へ合わせに行く。

これはスコープ外項目（⑩ の陳腐化・突合レポート §4 の改善提案）と異なり、**新機構が直接壊すもの**であるため、接続部として同一 PR に含める。

## 13. 未解決とリスク

- **n=0 である。** 本設計は manako の 1 回の突合と 3 件の裁定から起こしたものであり、インタビュー形式そのものはまだ一度も実施していない。初回投入の結果で手順を改訂する前提とする
- 入口 B（面の walkthrough）は入口 A より根拠が薄い。SKILL.md には両方を書くが、**B の記述は A と同じ密度で書かない**（裁定ループ・記録・打ち切りは共通なので、B 固有の差分だけを書く）。初回投入は A で行い、B の手順は初回実施の結果を見て改訂する
- 1セッション 5〜10 件という上限は実測に基づかない。初回投入で実際の疲労点を測り、改訂する
