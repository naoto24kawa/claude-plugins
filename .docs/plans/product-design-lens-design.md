# product-design-lens 設計書

## 1. 背景

`~/Downloads/プロダクト設計レンズ集.md`（300行）は、1つのプロダクトの要件定義で実際に通した設計レンズ19本と、その効果検証を記録した文書である。冒頭で「レンズの価値は網羅性ではなく、自分の判断を訂正する機会を強制的に作ること」と定義し、実際に3箇所で判断が覆った事実（グッズマスタの価値・堀の定義・三角トレードの優先度）を記録している。

これをスキル化する。既存の `lens-review-cycle` と名前・語彙が近いため、両スキルの責務境界を同時に定義し、双方に相互参照を配線する。

## 2. 棲み分け（軸B: 問いの種類で切る）

| | product-design-lens（新規） | lens-review-cycle（既存） |
|---|---|---|
| 問い | この判断は**外の世界に照らして**正しいか | この記述は**内部的に**破綻していないか |
| 見る先 | 競合・法令・時間・失敗シナリオ・コスト（**文書の外**） | 曖昧・矛盾・過剰・宙吊り参照（**文書の中**） |
| 成果 | **判断を書き換える** | **記述を直す** |
| 終端 | 全レンズ通過＋未裁定の訂正候補が0 | flag 0 |
| 実行 | 対話（訂正の採否は人間が裁定） | 自律（ラウンド間の確認なし） |

同じ要件定義書に両方を当てられるが、目的が直交するため競合しない。順番が生まれる——**判断を確定させてから（product-design-lens）、記述を締める（lens-review-cycle）**。

この軸は新たに発明した境界ではない。元文書自身が A 層「内側からのレンズ（作るものを決める）」／ B 層「外側からのレンズ（判断を訂正する）」という内外の軸で構成されており、その構造をそのまま2スキルの境界として採用する。

### 却下した軸

- **軸A（フェーズで切る）**: 「構想段階なら新スキル、成果物ができたら lens-review-cycle」。要件定義書も文章仕様であり lens-review-cycle の #6/#7 の対象に該当するため、同じファイルを両スキルが主張して破綻する。
- **軸C（対象の可変性で切る）**: 「まだ変えられる判断／確定した仕様」。軸Bに近いが「確定したか」の判定が主観的で、スキル起動時に機械的に判定できない。

## 3. product-design-lens の仕様

### 3.1 レンズ構成（元文書の A/B/C/D → 常設／条件付きへ再編）

元文書の D 層は「その案件で未実施だった」という履歴でグルーピングされている。スキルでは履歴ではなく**起動判定**で分ける。

**常設レンズ（12本・必ず通す）**

| ID | レンズ | 問い |
|---|---|---|
| A-1 | 機能要件 | 何ができて、何ができないか |
| A-2 | ユーザーストーリー | 実際の人が動いたとき、何が壊れるか |
| A-3 | 運用設計 | 誰がどう回すか。何が破綻の兆候か |
| A-4 | クレーム想定 | 何を言われるか。説明で解けるか、設計判断が問われるか |
| B-1 | 失敗（プレモータム） | 1年後にこのプロダクトは死んでいる。何が起きたか |
| B-2 | 法務・コンプライアンス | 何が違法になりうるか。どの判断が守ってくれているか |
| B-3 | 競合・参入 | 既存プレイヤーが同じことをしたら勝てるか。彼らがやらない理由は何か |
| B-4 | アクセシビリティ | 使えない人がいないか。対応は追加コストか |
| B-5 | 時間軸（2年目） | 永続資産が育った後、何が変わるか。その資産は本当に価値があるか |
| C-1 | データモデル | 後から変えられない構造は何か |
| C-2 | コスト試算 | いくらかかるか。コストの重心はどこか |
| D-3 | 計測 | 何を記録しておけば、後から判断できるか |

**D-3 計測を常設へ昇格する。** 元文書自身が発動条件を「常に必要」、優先度表で「実装前に必ず」と記しており、D 層に置かれているのは当該案件で未実施だったという理由に過ぎない。

**条件付きレンズ（7本・発動条件を判定して通す）**

| ID | レンズ | 発動条件 |
|---|---|---|
| D-1 | セキュリティ（攻撃者） | ①アカウントを持つ ②ユーザー間で何かをやり取りする ③金銭または金銭的価値のあるものを扱う — 1つでも該当 |
| D-2 | オンボーディング（1人目） | ①ネットワーク効果がある ②初回利用のハードルが成否を分ける ③無料で使い始められる — いずれか |
| D-4 | 価格・課金設計 | ①収益化を実際に始める ②「後から課金できる余地」を残す設計判断をする — ②の時点で軽く通す |
| D-5 | サポート | ①ユーザー数が問い合わせを生む規模になる ②操作が直感的でない機能がある — いずれか |
| D-6 | サービス終了・移行 | ①ユーザーが蓄積したデータを持つ ②撤退基準を数値で定めた — いずれか |
| D-7 | 国際化 | ①海外ユーザーが実際に現れた ②多言語化のコストが構造的に低い — ②なら早期に検討 |
| D-8 | チーム | ①2人目が加わる ②運用を誰かに任せる ③自分が離れる可能性がある — いずれか |

条件付きレンズは**非該当も記録する**（例: `D-8 チーム: 非該当（1人開発）`）。記録しないと「通し忘れ」と「該当なし」が区別できない。

### 3.2 通す順番

元文書の順序を採用する。

```
1. A-1 機能要件（境界を引く）
2. B-1 失敗（プレモータム）   ← 早いほど良い
   └ 成立の前提が未検証なら、ここで検証する
3. A-2 ユーザーストーリー（1巡目）
4. A-3 運用設計
5. B-3 競合・参入 / B-5 時間軸  ← 判断を訂正するレンズ
6. B-2 法務
7. A-2 ユーザーストーリー（2巡目）  ← 変更が生んだ穴を拾う
8. A-4 クレーム想定 / B-4 アクセシビリティ
9. C-1 データモデル / C-2 コスト / D-3 計測  ← 機能が固まってから
10. 条件付きレンズ（発動条件に該当するもの）
    └ ただし D-1 セキュリティのみ 9 の C-1 データモデル直後に置く（元文書の指定）
```

順番の根拠（元文書より）:
- **B-1 は早く**——プロダクトが成立するかの前提が未検証のまま設計を積み上げると全部が無駄になりうる
- **訂正のレンズ（B-3 / B-5）は中盤**——早すぎると訂正すべき判断がまだ無く、遅すぎると手戻りが大きい
- **A-2 は複数回**——設計を変更したら、その変更が生んだ穴を探すために再度回す

### 3.3 起動時の判定（3項目・いずれも対話で確定させる）

| 項目 | 判定方法 |
|---|---|
| 対象文書の有無 | 起動時の引数にパスがあればそれを使う。無ければ「対象の設計文書はあるか」を1回だけ問う。無いと答えられたら対話で構想を引き出す |
| プロダクト名 | 成果物ディレクトリ `<product-name>` に使う。対象文書があればその見出しから提案し、無ければ問う。kebab-case へ正規化する |
| 既存の進捗 | `.docs/product-lens/<product-name>/progress.md` が存在すれば再開する（判定は `references/progress-state.md` が正本） |

### 3.4 実行フロー（対話型）

```
起動 → 起動時の判定3項目（上表）
        ├─ あり: 読む
        └─ なし: プロダクト名＋一行説明を対話で引き出す
   ↓
条件付き7レンズの発動条件を判定 → 通すレンズ集合を確定・progress.md へ記録
   ↓
┌─ レンズ N を当てる ────────────────────────┐
│  1. そのレンズの問いで対象を検討               │
│  2. 出たものを2分類して提示                   │
│     ・訂正候補（既存の判断を覆す）             │
│     ・未定義（穴・未決事項）                   │
│  3. 人間が裁定: 採用 / 却下 / 保留             │
│  4. 裁定を訂正ログへ書く（元の記述は消さない）    │
└──────────────────────────────────────────┘
   ↓
再通過判定（下記の定義）→ 該当すれば既通過レンズを再通過候補に積む
   ↓
全レンズ通過 → 完了レポート → lens-review-cycle を推奨
```

**再通過の定義**: 採用された訂正が、既に通過したレンズの**前提**（そのレンズで確定させた判断）を変える場合、そのレンズを再通過候補に積む。どのレンズの前提を変えたかは訂正ログの記入時に人間が指定する（エージェントが推測しない）。積んだだけでは再通過しない——全レンズを一巡した後に候補をまとめて提示し、通すかどうかを人間が決める。

**このスキルはユーザーへの確認を行う。** lens-review-cycle の自律実行原則とは正反対である。訂正の採否を判定する客観基準が存在しないため（flag 0 に相当する終端が無い）、裁定は人間が行う。

### 3.5 裁定の3択

| 裁定 | 意味 | 必須付随情報 |
|---|---|---|
| 採用 | 判断を書き換える | 訂正ログへ（元の判断・訂正後・理由・どのレンズ） |
| 却下 | 指摘は当たらない | 却下理由（後から同じ議論を蒸し返さないため） |
| 保留 | 今は決めない | **再検討トリガー必須**（「Xが起きたら再検討」） |

**保留に再検討トリガーを必須とする。** 元文書が D 層で発見した「いつか必要では使われない。発動条件を書いておく」という知見を、裁定ルールへ横展開したもの。トリガーの無い保留は宙吊り状態となり、数ヶ月後に同じ議論が再発する。

### 3.6 成果物

元文書「使い方のコツ」の3点をそのままファイルにする。

```
.docs/product-lens/<product-name>/
  ├── progress.md      # 通したレンズ・裁定結果・非該当の記録（再開の正本）
  ├── corrections.md   # 訂正ログ（元の判断を消さずに残す）
  ├── not-doing.md     # やらないと決めたこと＋理由＋再検討トリガー
  └── lens/<id>.md     # レンズごとに何が出たか（出なかったことも記録）
```

**進捗の永続化は必須。** 最大19レンズを対話で通すと1セッションでは終わらない。`progress.md` を再開の正本とする。

### 3.7 終端条件

```
常設12レンズ通過
  ＋ 条件付き7レンズが「通過」または「非該当（理由つき）」
  ＋ 未裁定の訂正候補が0（保留は再検討トリガーつきで裁定済み扱い）
```

### 3.8 ファイル構成

| ファイル | 中身 |
|---|---|
| `SKILL.md` | 実行モデル・フロー・裁定ルール・終端条件（500行以下） |
| `references/lens-catalog.md` | 19レンズの問い・進め方・発動条件・実例 |
| `references/correction-log-format.md` | 訂正ログ / not-doing / progress の形式 |
| `references/progress-state.md` | 進捗の永続化と再開判定 |

元文書の「効果」ブロック（グッズ交換ツール固有の実例）は `lens-catalog.md` に**「実例（1案件からの観測）」と明示ラベルして隔離する**。ラベル無しで本文へ混ぜると一回性の一般化となり、lens-review-cycle の #7 Altitude Checker が正しく flag する状態になる。

## 4. lens-review-cycle 側の変更（4点）

| # | 対象 | 変更 | 規模 |
|---|---|---|---|
| 1 | `SKILL.md` frontmatter `description` | 棲み分け1文を追加（「プロダクト構想段階の判断訂正は product-design-lens を使う」） | 1行 |
| 2 | `SKILL.md` 冒頭 | 「このスキルを使わない場合」節を追加（product-design-lens への分岐） | 3〜5行 |
| 3 | `references/ambiguity-hunter.md` | **逆流ルール**を追加 | 1ブロック |
| 4 | `SKILL.md` ステップ6 完了レポート | 「判断レンズへの差し戻し」節を追加（#3 の逆流ルールが出した差し戻しの件数と、product-design-lens での裁定要求を報告する） | 3行 |

### 4.1 逆流ルール（#3 の内容）

#6 Ambiguity Hunter が「そもそもこの判断の根拠が無い」型の findings を出した場合、それは記述の曖昧さではなく**判断の未検証**である。明文化させず product-design-lens へ差し戻す。

逆流経路が無い場合の失敗経路:
```
#6 が「根拠を明文化せよ」と指摘
  → エージェントがもっともらしい根拠を後付けで書く
  → 誤った判断が「根拠つき」に格上げされて固定される
```

### 4.2 触らないもの

実行モデル節・FP レジストリ・durable-state・収束条件（最大3ラウンド）・7レンズ構成。既存の動作は変更しない。

## 5. 配置と整合性維持

```
~/projects/elchika-inc/agent-toolkit/
  skills/product-design-lens/          ← 正本（新規）
    SKILL.md
    references/{lens-catalog,correction-log-format,progress-state}.md
  skills/lens-review-cycle/            ← 4点の調整
    SKILL.md
    references/ambiguity-hunter.md
  plugins/dev-tools/skills/product-design-lens/  ← 同期コピー（cp -R）
  README.md                            ← スキル一覧に追記
  CLAUDE.md                            ← 「整合性の維持対象」表へ同期対象を1行追加
```

**standards リポジトリは変更しない。** agent-toolkit の CLAUDE.md が「ルールの中身を複製しない。skill は絞り込み・判定・レポート形式だけを持ち、検査項目は standards を読む」と定めており、19レンズは MUST ではなく手法であるため、standards（原則と MUST を持つリポジトリ）の対象外。

**plugins/dev-tools へ同期する。** lens-review-cycle が両所に同一バイトで存在しており、対で使うスキルが片方だけプラグインに無いと、プラグイン経由のユーザーにハンドオフ先が存在しない状態になる。

## 6. 検証 rubric

| # | 検証項目 | 方法 | 成功条件 |
|---|---|---|---|
| 1 | SKILL.md の行数上限 | `wc -l skills/product-design-lens/SKILL.md` | 500以下 |
| 2 | 外部参照が1階層 | ① `find skills/product-design-lens/references -mindepth 1 -type d` ② references 内の `references/*.md` 参照先が全て同 references 内に実在するか | ①0件（サブディレクトリなし） ②宙吊り0件 |
| 3 | frontmatter 必須項目 | `name` / `description` の存在 | 両方あり |
| 4 | 同期コピーがバイト一致 | `diff -r skills/product-design-lens plugins/dev-tools/skills/product-design-lens` | 差分なし |
| 5 | 相互参照が実在 | 両 SKILL.md が互いのスキル名を正しく綴っているか | 両方向とも実在するスキル名 |
| 6 | **スキルが正しく発火する** | 新セッションで両方向のトリガー語を入力 | 「プロダクト設計のレンズを通したい」→ product-design-lens ／「レビューサイクルを回して」→ lens-review-cycle |
| 7 | 既存 lens-review-cycle の非退行 | 変更した4箇所以外に差分が無いこと（`git diff`） | 実行モデル・FP レジストリ・収束条件・7レンズ構成に差分なし |

### 6.1 ベースライン実測（2026-08-25・既存 lens-review-cycle で取得）

rubric は書く前に既存スキルで実行し、検査が機能することを確認した。

| # | 実測値 | 判定 |
|---|---|---|
| 1 | `wc -l skills/lens-review-cycle/SKILL.md` = 251 | 上限500に対し余裕あり |
| 2 | references サブディレクトリ 0件 ／ 参照先4種すべて実在 | PASS（positive control 取得） |
| 4 | `diff -r skills/lens-review-cycle plugins/dev-tools/skills/lens-review-cycle` 差分なし | PASS（検査が機能する） |

**当初 rubric #2 を「references 内から更に参照していないこと＝参照0件」と書いていたが、実測により既存 lens-review-cycle が references 間で8件相互参照していることが判明したため破棄した。** agent-toolkit CLAUDE.md の「外部参照: 1階層まで」は「references より深い階層を作らない」の意であり、references 同士の参照は同一階層内で規約に反しない。決め打ちのまま採用していれば、worker が正しく作っても不合格になり「基準へ合わせるための改悪」を招いていた。

検証 #6 が本命である。description に棲み分けを書いても、実際にエージェントが正しく分岐するかは実測するまで分からない（「記述は到達を意味しない」）。名前が近いスキルを2つ並べるため、誤発火が起きるならここである。#4 も同種で、`cp -R` を忘れると片側だけ古くなるが見た目では判別できない。
