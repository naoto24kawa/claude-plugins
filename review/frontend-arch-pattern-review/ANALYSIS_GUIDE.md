# フロントエンドアーキテクチャ トレードオフ分析ガイド

複数のエージェントから得られた提案を統合し、相反する推奨事項のバランスを取るための分析手法です。

---

## トレードオフパターン

### パターン 1: Feature分割粒度 vs 開発スピード

| 観点 | 細かい分割 | 粗い分割 |
|------|-----------|---------|
| 状況 | 再利用性重視、大規模チーム | 開発速度重視、小規模チーム |
| 判断基準 | 複数箇所で使う | 1箇所でしか使わない |
| 優先 | 保守性・再利用性 | 開発速度・シンプルさ |

**調整方法**:
- 現在の再利用実績で判断
- 将来の再利用は予測しすぎない
- 必要になったら分割する YAGNI 原則

### パターン 2: loader でのデータ取得 vs クライアントサイドフェッチ

| 観点 | loader | クライアント |
|------|--------|-------------|
| 状況 | ページ遷移時のデータ | インタラクション後のデータ |
| 判断基準 | ページ表示に必須 | ユーザーアクション後に必要 |
| メリット | SSR対応、型安全 | 柔軟、リアルタイム更新 |

**調整方法**:
- 初期表示に必要なデータは loader
- ユーザーアクション後のデータは適宜判断
- 無限スクロールなどは組み合わせ

### パターン 3: サーバー状態 vs クライアント状態

| 観点 | サーバー状態 | クライアント状態 |
|------|------------|-----------------|
| 管理方法 | loader/action | useState/useContext |
| 例 | APIデータ、フォーム結果 | モーダル開閉、タブ選択 |
| キャッシュ | React Router が管理 | 自前管理 |

**調整方法**:
- APIから取得したデータはサーバー状態
- UI の一時的な状態はクライアント状態
- 迷ったらサーバー状態を優先

### パターン 4: 型安全性 vs 実装柔軟性

| 観点 | 型安全性優先 | 柔軟性優先 |
|------|------------|-----------|
| 状況 | 安定したAPI | 頻繁に変わるAPI |
| 判断基準 | 型エラーで問題検出 | 迅速な対応が必要 |
| リスク | 型定義の保守コスト | ランタイムエラー |

**調整方法**:
- Hono RPC で自動的に型安全を確保
- unknown を避け、適切な型を定義
- any は禁止

## 優先度判定マトリクス

### Critical（即時対応）

- Feature間の循環依存
- 型安全性の破壊（any の使用）
- セキュリティリスク（認証トークンの露出など）

### High（今Sprint内）

- レイヤー境界違反（features → shared への逆依存）
- loader/action を使わないデータ取得
- エラーハンドリングの欠如

### Medium（次Sprint）

- コンポーネントの分割不足
- Context の最適化
- 再利用可能なコンポーネントの抽出

### Low（バックログ）

- 命名規則の統一
- ドキュメント追加
- パフォーマンス最適化

## 相反する提案の調整

### 複数エージェントの提案が矛盾する場合

1. **型安全性を最優先**: 型が壊れる変更は避ける
2. **保守性を次に優先**: 長期的なメンテナンスコストを考慮
3. **パフォーマンスは計測後**: 推測ではなく実測データで判断
4. **開発速度は最後**: 品質を犠牲にしない

### 調整の例

**FSD vs Router**:
- 「Feature を細かく分割すべき」vs「ルートファイルをシンプルに保つべき」
- → Feature は論理的な境界、ルートは物理的な配置として分けて考える

**State vs API**:
- 「状態を Context で管理すべき」vs「loader で取得すべき」
- → サーバーデータは loader、UI状態のみ Context

**Component vs FSD**:
- 「共通コンポーネントを shared に」vs「Feature 内に閉じ込める」
- → 2箇所以上で使うなら shared、1箇所なら Feature 内
