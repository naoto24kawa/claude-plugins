## アーキテクチャ準拠メトリクス

### 1. レイヤー境界違反数

**定義**: 不正なレイヤー間依存の数

**測定方法**:

```bash
# Domain層での違反検出
grep -r "from '.*\/infrastructure\/" domain/
grep -r "from '.*\/application\/" domain/
grep -r "from '.*\/presentation\/" domain/

# Application層での違反検出
grep -r "from '.*\/infrastructure\/" application/
grep -r "from '.*\/presentation\/" application/
```

**目標値**:

- **0件が理想**
- 新規コードでの違反: 0件必須
- 既存コードでの違反: 段階的に削減

**改善のヒント**:

- 依存性注入（DI）の導入
- インターフェースの活用
- 段階的なリファクタリング

---

### 2. 依存方向違反数

**定義**: 外側から内側への正しい依存方向に反する依存の数

**測定方法**:

```bash
# 循環依存の検出
npx madge --circular src/

# 依存グラフの生成
npx madge --image graph.svg src/
```

**目標値**:

- 循環依存: **0件**
- 不正な依存方向: **0件**

**改善のヒント**:

- 循環依存の解消にはインターフェース抽出が有効
- 依存グラフを定期的に確認

---

### 3. DIP（依存性逆転）準拠率

**定義**: Repository等のインターフェース定義と実装分離の達成率

**測定方法**:

```bash
# インターフェース定義数
grep -r "interface.*Repository" domain/ | wc -l

# 実装数
grep -r "implements.*Repository" infrastructure/ | wc -l
```

**計算式**:

```
DIP準拠率 = (インターフェース経由の依存数 / 外部サービス依存数) × 100
```

**目標値**:

- 外部サービス連携: **100%**
- データベースアクセス: **90%以上**
- 内部ユーティリティ: 省略可

## 設計品質メトリクス

### 1. DDD Building Blocks準拠率

**定義**: 各Building Blockの正しい実装率

**測定方法**:

各Building Blockについて以下をチェック:

| Building Block | チェック項目 |
|---------------|-------------|
| Entity | ID存在、equals実装、カプセル化 |
| Value Object | 不変性、equals実装、バリデーション |
| Aggregate Root | 整合性保証、Event発行、ID参照 |
| Repository | Interface/Impl分離、ドメイン言語 |
| Domain Service | ステートレス、複数集約操作 |
| Domain Event | 過去形命名、不変性、発生日時 |

**目標値**:

- **80%以上が理想**
- 重要なドメインロジック: 90%以上

---

### 2. 集約境界の適切性

**定義**: 集約の設計が適切かどうかの評価

**チェック項目**:

- [ ] 集約が他の集約を直接参照していないか（ID参照のみ）
- [ ] 集約サイズが適切か（大きすぎ/小さすぎ）
- [ ] トランザクション境界が適切か

**目標**:

- 集約間の直接参照: **0件**
- 適切なサイズの集約: **80%以上**

---

### 3. Bounded Context整合性

**定義**: フロントエンド/バックエンド間のContext対応の一貫性

**測定方法**:

```
Backend Contexts と Frontend Features のマッピング表を作成し、
対応関係の明確さを評価
```

**目標値**:

- 明確な対応関係: **90%以上**
- Anti-Corruption Layer必要箇所の実装: **100%**

## 設定整合性メトリクス

### 1. バインディング整合性率

**定義**: wrangler.jsoncと型定義（Env）の整合性

**測定方法**:

```bash
# wrangler.jsonc からバインディング名を抽出
jq '.d1_databases[].binding, .r2_buckets[].binding, .queues.producers[].binding' wrangler.jsonc

# 型定義からバインディング名を抽出
grep -E "^\s+\w+\??: (D1Database|R2Bucket|Queue)" packages/types/src/env.ts
```

**計算式**:

```
整合性率 = (一致するバインディング数 / 全バインディング数) × 100
```

**目標値**:

- **100%** （不一致は即座に修正）

---

### 2. 環境変数カバレッジ

**定義**: 必要な環境変数の定義率

**測定方法**:

```bash
# コード中で使用されている環境変数
grep -r "c.env\.\w\+" apps/ | grep -oP "c\.env\.\K\w+" | sort -u

# 型定義されている環境変数
grep -E "^\s+\w+\??" packages/types/src/env.ts | grep -oP "^\s+\K\w+"
```

**目標値**:

- **100%** （未定義の環境変数アクセスは0件）

---

### 3. ポート設定整合性

**定義**: 各サービスのポート設定が期待値と一致しているか

**期待値例**:

| サービス | 期待ポート |
|---------|----------|
| Frontend | 5173 |
| Admin | 5174 |
| Backend | 8787 |
| Images | 8788 |

**目標値**:

- **100%一致**

## 測定方法とツール

### 推奨ツール

#### 依存関係分析

- **madge**: 循環依存検出、依存グラフ生成
- **dependency-cruiser**: 依存関係ルール検証

#### コード分析

- **ESLint**: カスタムルールで命名規則等を検証
- **TypeScript**: 型チェックで設定整合性を検証

#### Cloudflare設定

- **wrangler**: 設定の検証
- **jq**: JSONの解析

### 自動化スクリプト例

```bash
#!/bin/bash
# アーキテクチャ準拠チェックスクリプト

echo "=== レイヤー境界違反チェック ==="
DOMAIN_VIOLATIONS=$(grep -r "from '.*\/infrastructure\/" src/domain/ 2>/dev/null | wc -l)
echo "Domain層からInfrastructure層への依存: $DOMAIN_VIOLATIONS 件"

echo ""
echo "=== 循環依存チェック ==="
npx madge --circular src/ 2>/dev/null || echo "循環依存なし"

echo ""
echo "=== DIP準拠チェック ==="
INTERFACES=$(grep -r "interface.*Repository" src/domain/ 2>/dev/null | wc -l)
IMPLEMENTATIONS=$(grep -r "implements.*Repository" src/infrastructure/ 2>/dev/null | wc -l)
echo "Repository Interface: $INTERFACES 件"
echo "Repository Implementation: $IMPLEMENTATIONS 件"
```

## 目標設定のガイドライン

### SMART原則に基づく目標設定

**Specific（具体的）**: "アーキテクチャを改善する" ではなく "レイヤー境界違反を10件から0件に削減"

**Measurable（測定可能）**: 上記のメトリクスで測定できる

**Achievable（達成可能）**: 現実的な目標値を設定

**Relevant（関連性）**: プロジェクトの品質目標と連動

**Time-bound（期限付き）**: "1ヶ月以内に"などの期限を設定

### 目標設定の例

#### 短期目標（1-2週間）

- [ ] レイヤー境界違反を0件に
- [ ] 循環依存を解消
- [ ] バインディング整合性100%達成

#### 中期目標（1-2ヶ月）

- [ ] DIP準拠率を90%以上に
- [ ] DDD Building Blocks準拠率を80%以上に
- [ ] Bounded Context整合性を90%以上に

#### 長期目標（3-6ヶ月）

- [ ] すべてのメトリクスで目標値達成
- [ ] 自動チェックのCI/CD統合
- [ ] アーキテクチャドキュメントの整備

## まとめ

成功指標の活用ポイント：

1. **ベースラインを測定**: まず現状を把握
2. **優先度を決定**: Critical > High > Medium > Low
3. **定期的にレビュー**: 週次でメトリクスを確認
4. **CI/CDに統合**: 自動チェックで継続的に監視
5. **チームで共有**: 透明性を保ち、全員で改善に取り組む
