## 相反する提案の特定

### ステップ 1: 提案のカテゴリ分類

各エージェントの提案を以下のカテゴリに分類：

- **レイヤー構造**: 層の分離、責任の配置
- **DDDパターン**: Building Blocksの実装、集約境界
- **依存関係**: 依存方向、DIP準拠
- **フロントエンド**: Feature構成、ルーティング、状態管理
- **インフラ設定**: Cloudflareバインディング、環境変数

### ステップ 2: 矛盾の検出

同じ対象に対して異なる推奨がある場合を特定：

```
例:
- レイヤー構造: "Application層にビジネスロジックを移動すべき"
- DDD: "このロジックはDomain Serviceに属すべき"
```

### ステップ 3: 影響範囲の評価

各提案が他の部分に与える影響を分析：

- **直接影響**: 変更対象のコード自体
- **間接影響**: 依存するコード、呼び出し元
- **波及影響**: システム全体、チームの開発フロー

## トレードオフのパターン

### パターン 1: 厳格なDDD vs 実用性

**状況**: DDD Building Blocksの完全準拠とシンプルな実装のバランス

**判定基準**:

- ドメインの複雑さが低い → シンプルな実装優先
- ドメインの複雑さが高い → DDD優先
- チームのDDD習熟度が低い → 段階的導入
- 変更頻度が高いドメイン → DDD優先

**推奨アプローチ**:

```typescript
// 複雑なドメイン: DDDパターン適用
export class Order {
  private readonly id: OrderId;
  private items: OrderItem[];
  private status: OrderStatus;

  addItem(item: OrderItem): void {
    this.validateCanAddItem();
    this.items.push(item);
    this.events.push(new OrderItemAdded(this.id, item));
  }
}

// シンプルなドメイン: 軽量な実装
interface Config {
  key: string;
  value: string;
}
```

---

### パターン 2: レイヤー分離 vs 開発スピード

**状況**: 厳格なレイヤー境界とアジャイルな開発のバランス

**判定基準**:

- 小規模プロジェクト（〜5ファイル） → 柔軟な構造
- 中規模プロジェクト（〜50ファイル） → 基本的なレイヤー分離
- 大規模プロジェクト（50ファイル以上） → 厳格なレイヤー分離
- MVPフェーズ → 柔軟な構造、後でリファクタリング

**推奨アプローチ**:

```
小規模:
src/
├── api/
├── domain/
└── db/

大規模:
src/
├── presentation/
├── application/
├── domain/
└── infrastructure/
```

---

### パターン 3: フロントエンド/バックエンド境界整合性

**状況**: Bounded ContextとFeatureの対応

**判定基準**:

- 1:1対応が自然 → 厳格に対応
- UIの都合でまとめる必要がある → フロントエンドで適切に抽象化
- バックエンドの都合で分割されている → Anti-Corruption Layer検討

**推奨アプローチ**:

```
Backend Contexts:     Frontend Features:
├── Card             ├── card (1:1対応)
├── Pack             │
├── Gacha           └── gacha (Pack+Gachaを統合)
└── News             └── news (1:1対応)
```

---

### パターン 4: 依存関係の厳格性 vs 現実的な実装

**状況**: DIP準拠と実装コストのバランス

**判定基準**:

- 外部サービス連携 → インターフェース必須
- 単純なCRUD → インターフェース省略可
- テスト容易性が重要 → インターフェース必須
- プロトタイプ → 省略可、後で追加

**推奨アプローチ**:

```typescript
// 外部サービス: インターフェース必須
interface PaymentGateway {
  charge(amount: Money): Promise<PaymentResult>;
}

// 単純なCRUD: 直接実装でも可
class ConfigRepository {
  constructor(private db: D1Database) {}
  async get(key: string): Promise<string | null> {
    return this.db.prepare('SELECT value FROM config WHERE key = ?').bind(key).first();
  }
}
```

## 優先度判定基準

### Critical（即時対応）

以下のいずれかに該当：

1. **セキュリティ**
   - 認証・認可の設計不備
   - 機密情報の漏洩リスク

2. **データ整合性**
   - 集約境界の設計ミス
   - トランザクション境界の問題

3. **システム安定性**
   - 循環依存
   - 不正なレイヤー依存

### High（優先対応）

1. **保守性への大きな影響**
   - レイヤー境界違反の蓄積
   - DDDパターンの大幅な逸脱

2. **将来的な拡張の阻害**
   - 密結合による変更困難性
   - 不適切な集約設計

### Medium（計画的に対応）

1. **設計品質の向上**
   - Value Objectの導入
   - Repository Interfaceの追加

2. **一貫性の改善**
   - 命名規則の統一
   - ディレクトリ構造の整理

### Low（将来的な改善）

1. **ベストプラクティス適用**
   - Domain Eventの導入
   - Anti-Corruption Layerの追加

## 意思決定フレームワーク

### デシジョンツリー

```
提案が相反する
  ├─ セキュリティに関わる？
  │   └─ Yes → セキュリティ優先
  │   └─ No → 次へ
  │
  ├─ データ整合性に関わる？
  │   └─ Yes → 整合性優先
  │   └─ No → 次へ
  │
  ├─ システムの安定性に関わる？
  │   └─ Yes → 安定性優先
  │   └─ No → 次へ
  │
  ├─ 実装コストは？
  │   ├─ 高い → シンプルな方を選択、段階的改善
  │   └─ 低い → 理想的な設計を選択
  │
  └─ チームの習熟度は？
      ├─ 低い → 理解しやすい方を選択
      └─ 高い → より高度な設計を選択
```

### チェックリスト

相反する提案を評価する際のチェックリスト：

- [ ] どちらの提案もセキュリティリスクはないか？
- [ ] 実装コストと効果のバランスは妥当か？
- [ ] チームのスキルレベルで実装・保守可能か？
- [ ] 既存システムとの互換性は保たれるか？
- [ ] テストは十分に書けるか？
- [ ] 将来的な拡張性は確保されるか？

## 段階的アプローチ

相反する提案がある場合の段階的実装：

```
Phase 1: まず安全性を確保（セキュリティ、データ整合性）
  ↓
Phase 2: 次に基盤を整備（レイヤー構造、依存方向）
  ↓
Phase 3: その後設計品質を向上（DDDパターン、一貫性）
  ↓
Phase 4: 最後にベストプラクティス適用
```
