このスキルは、AIが理解・実装しやすいアプリケーション仕様書を作成するための標準定義を提供する。

## 使い方

### 仕様書作成時

新規プロジェクトで仕様書を作成する際、または既存仕様書を改善する際:

#### ステップ1: 標準定義の読み込み
- `references/spec-definition.md`を読み込む
- **検証**: 11種類の仕様書種別とそれぞれの必須記述項目を理解できたか確認
- **エラー時**: 不明な点がある場合、該当セクションを再読込し、具体例を参照

#### ステップ2: 仕様書種別の選択
- プロジェクトの特性に応じて必要な仕様書種別を選択
- **検証**: 選択した種別がプロジェクト要件を十分にカバーしているか確認
- **エラー時**: カバーできていない要件がある場合、追加の種別を検討するか、既存種別の拡張を検討

#### ステップ3: 必須項目の記述
- 各仕様書種別の「必須記述項目」に従って記述
- **検証**:
  - Frontmatter（type/title/version/updated）が正しく記述されているか確認
  - すべての必須セクションが含まれているか確認
  - 型定義が具体的で明示的か確認
- **エラー時**: 不足項目がある場合、該当セクションの定義を参照して追加
- **出力**: 完成した仕様書ファイルのパスと種別を表示

##### 記述品質の原則

**型定義の明示性:**
- ❌ 避けるべき: `object`、`any`、`unknown` などの曖昧な型
- ✅ 推奨: リテラル型、ユニオン型、具体的なインターフェース名
- ✅ 制約を明記: 文字数制限、形式（UUID、ISO 8601など）、許可される値の列挙

**バリデーション責任の分離:**
- フロントエンド: 即時フィードバック用の基本的なチェック
- バックエンド: 最終検証とセキュリティ対策
- 各層の責任範囲を明確に定義

### 仕様書レビュー時

既存の仕様書をレビューする際:

#### ステップ1: 準備とチェックリスト選択
- 対象仕様書を読み込む
- Frontmatterから種別（type）を確認
- `references/review-checklist.md`を読み込む
- 該当する種別のチェックリストセクションを特定
- **検証**: 種別が11種類のいずれかに該当するか確認
- **エラー時**: 不明な種別の場合、最も近い種別を提案するか、共通チェック項目のみでレビュー

#### ステップ2: 共通チェック項目の評価
- Frontmatter（type/title/version/updated）の確認
- 構造と形式（見出し階層、マークダウン、型定義）の確認
- 明示性（暗黙の前提、境界条件、依存関係）の確認
- 具体性（具体例、制約条件）の確認
- **検証**: 各項目が準拠/部分的準拠/未準拠のいずれかを判定
- **エラー時**: 問題点を具体的に記録し、改善案を準備

#### ステップ3: 種別固有チェック項目の評価
- 該当種別の必須項目を確認
  - API仕様書: API種別、認証要件、バリデーション責任分担
  - コンポーネント仕様書: Props定義、アクセシビリティ要件
  - ページ仕様書: URL定義、データフロー、状態管理
  - データモデル仕様書: フィールド定義、インデックス設計
  - ビジネスロジック仕様書: メソッド詳細、トランザクション境界
- **検証**: すべての必須項目が含まれているか確認
- **エラー時**: 不足項目を具体的にリストアップし、優先度を付与

#### ステップ4: 総合評価とグレード算出
- 準拠率を計算（準拠項目数 / 総チェック項目数）
- 総合評価グレードを算出
  - A: 90%以上準拠
  - B: 70-89%準拠
  - C: 50-69%準拠
  - D: 30-49%準拠
  - F: 30%未満準拠
- **検証**: 評価が妥当か確認（極端に高い/低い場合は再確認）
- **出力**: 総合評価グレードと準拠率

#### ステップ5: レビューレポート作成
- `templates/review-report-template.md`をベースにレポートを作成
- 以下のセクションを記入:
  - エグゼクティブサマリー（総合評価、主要な発見事項）
  - 詳細評価（共通チェック、種別固有チェック）
  - 優先度別改善タスク（Critical/High/Medium/Low）
  - 具体的な修正例（修正前/修正後の対比）
  - 改善実施プラン（Phase別）
- **検証**: レポートが具体的で実行可能な内容か確認
- **出力**: 完成したレビューレポート

#### ステップ6: 改善提案の優先順位付け
- Critical問題: 即時対応が必要（仕様書が機能しない問題）
- High問題: 優先的に対応すべき（AI実装時の誤解を招く問題）
- Medium問題: 計画的に対応（品質向上のための改善）
- Low問題: 将来的な改善（より良い仕様書にするための提案）
- **検証**: 優先度付けが適切か確認
- **出力**: 優先度付きの改善提案リスト

### レビュー実施のヒント

**効率的なレビュー**:
- 共通チェック項目を先に評価することで、種別固有の評価がスムーズに
- チェックリストを機械的に適用せず、プロジェクト特性を考慮
- 良い点もレポートに記載してバランスの取れた評価を

**品質の高いレポート作成**:
- 問題点だけでなく、具体的な改善案を必ず提示
- 修正前/修正後の対比例を含めて理解しやすく
- 優先度を明確にして、何から着手すべきか分かりやすく

## 期待される出力

### 仕様書作成時

完成した仕様書ファイルは以下の形式で出力される:

- **ファイル名**: ケバブケース（例: `user-authentication.md`）
- **配置場所**: `specs/` ディレクトリ（デフォルト）
- **Frontmatter**: 必須メタデータを含む
  ```yaml
  ---
  type: api | component | page | data-model | business-logic | integration | auth | batch | infrastructure | overview | architecture
  title: 仕様書のタイトル
  version: 1.0.0
  updated: 2024-01-01
  ---
  ```
- **テンプレート**: `templates/` 配下の該当テンプレートに基づく構造
- **出力メッセージ**: ファイルパスと種別を表示
  ```
  ✓ API仕様書を作成しました: specs/user-authentication.md
  種別: api
  バージョン: 1.0.0
  ```

### レビュー時

レビューレポートは `templates/review-report-template.md` の形式で出力される:

- **エグゼクティブサマリー**: 総合評価グレード（A-F）、準拠率、主要な発見事項
- **詳細評価**:
  - 共通チェック項目の評価結果
  - 種別固有チェック項目の評価結果
- **優先度別改善タスク**: Critical/High/Medium/Low で分類
- **具体的な修正例**: 修正前/修正後の対比
- **改善実施プラン**: Phase別の実施計画

**出力例**:
```
# 仕様書レビューレポート

## 総合評価: B (75%準拠)

### 主要な発見事項
- ✅ Frontmatterが適切に記述されている
- 🟡 バリデーション責任分担が不明確
- ❌ エラーレスポンス定義が不足
...
```

### 詳細な標準定義

完全な仕様書標準定義は `references/spec-definition.md` を参照すること。

この標準定義には以下が含まれる:

- 11種類の仕様書ファイル定義(概要、アーキテクチャ、データモデル、API、コンポーネント、ページ、ビジネスロジック、統合、認証・認可、バッチ、インフラ)
- 各仕様書に記述すべき内容の詳細
- Frontmatterによるメタデータ管理方法
- REST/GraphQL両対応のAPI仕様書定義
- フロントエンド/バックエンドのバリデーション戦略

## 重要な原則

### 明示性優先
暗黙の前提を置かず、すべての情報を明示的に記述する

### 構造化
マークダウンの見出し構造を活用し、階層を明確にする

### 型定義の徹底
データ構造は具体的な型で記述する

### バリデーション責任の分離
フロントエンド(即時フィードバック)とバックエンド(最終検証)の責任を明確に分ける

### メタデータ管理
すべての仕様書はFrontmatterで必須メタデータ(type/title/version/updated)を管理する

## デフォルト設定

ユーザーから特に指示がない限り、以下の設定を適用:

### ファイル形式
- **フォーマット**: Markdown (.md)
- **Frontmatter**: YAML形式
- **文字エンコーディング**: UTF-8

### メタデータ
- **バージョニング**: セマンティックバージョニング (1.0.0)
- **日付形式**: YYYY-MM-DD (ISO 8601)
- **初回バージョン**: 1.0.0

### 記述スタイル
- **型定義**: TypeScript風記法
- **コード例**: 言語名を明示したコードブロック
- **見出しレベル**: 最上位を ## から開始（# はタイトル用）

### ファイル配置
- **推奨ディレクトリ**: プロジェクトルート直下の `specs/`
- **ファイル命名**: ケバブケース (例: `user-authentication.md`)
