## 共通チェック項目

すべての仕様書に適用されるチェック項目。

### 1. Frontmatter（優先度: Critical）

- [ ] **typeフィールドが存在する**
  - 値が11種類のいずれかに該当: `overview` / `architecture` / `api` / `component` / `page` / `service` / `integration` / `auth` / `job` / `infrastructure` / `database-schema`
  - 不備の場合: 仕様書の種別が不明確

- [ ] **titleフィールドが存在し、説明的である**
  - 単なる「API仕様書」ではなく「ユーザー作成API仕様書」など具体的
  - 不備の場合: 仕様書の識別が困難

- [ ] **versionフィールドが存在し、セマンティックバージョニング形式**
  - 形式: `X.Y.Z`（例: `1.0.0`）
  - 不備の場合: バージョン管理が不適切

- [ ] **updatedフィールドが存在し、ISO 8601形式**
  - 形式: `YYYY-MM-DD`
  - 不備の場合: 更新日が不明確

### 2. 構造と形式（優先度: High）

- [ ] **見出し階層が適切**
  - `#` はタイトルのみ、本文は `##` から開始
  - 見出しレベルのスキップがない（`##` → `####` など）
  - 不備の場合: 文書構造が分かりにくい

- [ ] **マークダウン形式が正しい**
  - コードブロックに言語指定がある
  - テーブル形式が正しい
  - 不備の場合: レンダリングエラーが発生

- [ ] **型定義がTypeScript風記法で記述されている**
  - 曖昧な「オブジェクト」ではなく `{ field: type }` 形式
  - 不備の場合: 型が不明確でAI実装が困難

### 3. 明示性（優先度: High）

- [ ] **暗黙の前提がない**
  - すべての情報が明示的に記述されている
  - 「一般的な方法で」などの曖昧な表現がない
  - 不備の場合: AIが誤った実装をする可能性

- [ ] **境界条件が記述されている**
  - 正常系だけでなくエラーケースも記述
  - エッジケースの扱いが明確
  - 不備の場合: エラーハンドリングが不完全

- [ ] **依存関係が明示されている**
  - 他の仕様書への参照が明確
  - 外部システムへの依存が記述
  - 不備の場合: 実装時に必要な情報が不足

### 4. 具体性（優先度: Medium）

- [ ] **具体例が含まれている**
  - 抽象的な説明だけでなく具体例がある
  - リクエスト/レスポンスの実例がある
  - 不備の場合: 理解が困難

- [ ] **制約条件が具体的**
  - 「短い文字列」ではなく「1-100文字」
  - 「大量のデータ」ではなく「最大10,000件」
  - 不備の場合: 実装時に判断できない

## 仕様書種別ごとのチェック項目

### API仕様書

#### 必須項目チェック

- [ ] **API種別が明記されている**
  - REST API / GraphQL API のいずれか明示
  - 不備の場合: 実装方式が不明

- [ ] **認証・認可要件が記述されている**
  - 認証方式（JWT / セッション等）
  - 必要な権限レベル
  - 不備の場合: セキュリティリスク

- [ ] **エンドポイント一覧（REST）またはスキーマ定義（GraphQL）が存在する**
  - すべてのエンドポイント/操作が列挙されている
  - 不備の場合: APIの全体像が不明

#### バリデーション定義

- [ ] **フロントエンド責務とバックエンド責務が明確に分離されている**
  - どちらで何を検証するか明記
  - 不備の場合: 二重検証または検証漏れが発生

- [ ] **バリデーションルールが具体的**
  - 「メールアドレス形式」「8文字以上」など具体的
  - 不備の場合: バリデーション実装が曖昧

- [ ] **エラーメッセージが定義されている**
  - ユーザー向けの表示文言が明記
  - 不備の場合: エラー時のUXが不明確

#### REST API固有

- [ ] **HTTPメソッドが適切**
  - GET: 取得、POST: 作成、PUT/PATCH: 更新、DELETE: 削除
  - 不備の場合: RESTful設計に違反

- [ ] **ステータスコードが明記されている**
  - 成功時・エラー時のコードが明確
  - 不備の場合: クライアント側のエラーハンドリングが困難

- [ ] **リクエスト・レスポンスの型定義が存在する**
  - パラメータ、ボディ、レスポンスすべてに型定義
  - 不備の場合: 型安全性が損なわれる

#### GraphQL API固有

- [ ] **スキーマ定義が完全**
  - Query/Mutation/Subscription、カスタム型すべて定義
  - 不備の場合: GraphQLスキーマ生成ができない

- [ ] **Resolver仕様が記述されている**
  - データ取得元、N+1問題対策
  - 不備の場合: パフォーマンス問題が発生

- [ ] **エラーハンドリング戦略が明確**
  - エラーコード体系、部分的成功の扱い
  - 不備の場合: エラー処理が不統一

## 品質評価基準

### 評価基準

各チェック項目の評価:

- **準拠**: すべての要件を満たしている
- **部分的準拠**: 一部の要件を満たしているが改善の余地がある
- **未準拠**: 要件を満たしていない

### 総合評価グレード

| グレード | 基準 | 説明 |
|---------|------|------|
| A | 90%以上準拠 | 優秀。AIが正確に実装できる |
| B | 70-89%準拠 | 良好。一部改善が必要 |
| C | 50-69%準拠 | 普通。多くの改善が必要 |
| D | 30-49%準拠 | 不十分。大幅な改善が必要 |
| F | 30%未満準拠 | 不合格。全面的な見直しが必要 |

## レビュー実施手順

### 1. 準備

- 対象仕様書を読み込む
- Frontmatterから種別（type）を確認
- 該当する種別のチェックリストを準備

### 2. 共通チェック

- 共通チェック項目をすべて確認
- 不備があれば記録

### 3. 種別固有チェック

- 該当種別のチェック項目をすべて確認
- 不備があれば記録

### 4. 評価とレポート作成

- 各項目の準拠状況を集計
- 総合評価グレードを算出
- レビューレポートを作成（`templates/review-report-template.md` 使用）

### 5. 改善提案

- 優先度付きの改善提案リストを作成
- Critical → High → Medium → Low の順に対応

---

## チェックリスト使用上の注意

1. **機械的にチェックしない**: 各項目の「なぜ必要か」を理解してチェック
2. **プロジェクト特性を考慮**: すべての項目が必須ではなく、プロジェクトに応じて判断
3. **改善提案を具体的に**: 「不足している」だけでなく「どう改善するか」を提案
4. **ポジティブフィードバックも**: 良い点も記録してモチベーション維持
