## 概要

本ドキュメントは「仕様書の仕様書」である。
AIが理解・実装しやすいアプリケーション仕様書を作成するために、各仕様書ファイルに何を記述すべきかを定義する。
具体的な記述方法やテンプレートは各プロジェクトが決定する。

---

## 共通原則

### Frontmatterによるメタデータ管理

すべての仕様書ファイルは、YAML形式のfrontmatterでメタデータを管理する。

#### 必須メタデータ
```yaml
---
type: string              # 仕様書種別(overview/architecture/api/component/page/service/integration/auth/job/infrastructure)
title: string             # 仕様書タイトル
version: string           # バージョン(セマンティックバージョニング推奨: 1.0.0)
updated: string           # 最終更新日(YYYY-MM-DD)
---
```

#### 推奨メタデータ
```yaml
tags: [string, ...]       # 分類タグ(feature名、ドメイン名等) - JSON配列形式
related: [string, ...]    # 関連する仕様書ファイルパス(相対パス) - JSON配列形式
dependencies: [string, ...]  # 依存する仕様書ファイルパス(相対パス) - JSON配列形式
```

**記述形式の注意:**
- ✅ 推奨: JSON配列形式 `tags: [frontend, authentication, api]`
- ✅ 空配列の場合: `tags: []`
- ❌ 非推奨: YAMLリスト形式（`tags:\n  - frontend`）

#### メタデータの用途
- **type**: AIが仕様書の種類を識別し、適切な解釈を行う
- **version**: 仕様変更の履歴管理とブレイキングチェンジの把握
- **related/dependencies**: 仕様書間の関係を明示し、AIが必要な情報を辿れるようにする

### 記述の基本方針
- **明示性**: 暗黙の前提を置かず、すべての情報を明示的に記述
- **構造化**: マークダウンの見出し構造を活用し、階層を明確に
- **型定義**: データ構造は具体的な型で記述(TypeScript風/JSON Schema風)
- **例示**: 抽象的な説明だけでなく具体例を必ず含める
- **境界条件**: 正常系だけでなくエッジケース・エラーケースも記述

### すべての仕様書に含めるべき項目
1. **目的**: このファイルが定義する対象と目的
2. **依存関係**: 他の仕様書や外部システムへの依存

## 仕様書ファイル種別定義

### 1. プロジェクト概要仕様書

**ファイル名パターン**: `overview.md`, `00-overview.md`

**目的**: プロジェクト全体の目的、スコープ、制約条件を定義

**必須記述項目**:
- プロジェクトの目的・背景
- 主要なユースケース(3-5個程度)
- 技術スタック概要
- システム境界(何を含み、何を含まないか)
- 主要な制約条件(パフォーマンス、セキュリティ等)
- 用語集(プロジェクト固有の用語定義)

**AI実装に必要な情報**:
- ビジネスドメインの基礎知識
- 全体のコンテキスト理解
- 優先順位付けの判断基準

---

### 2. アーキテクチャ仕様書

**ファイル名パターン**: `architecture.md`, `01-architecture.md`

**目的**: システム全体の構造と主要コンポーネント間の関係を定義

**必須記述項目**:
- システム構成図(テキストまたはMermaid)
- レイヤー構成(プレゼンテーション/ビジネスロジック/データアクセス等)
- 主要コンポーネント一覧と責務
- データフロー概要
- 外部システム連携ポイント
- セキュリティアーキテクチャ概要

**AI実装に必要な情報**:
- コンポーネント間の依存方向
- 責任範囲の明確な分離
- 通信プロトコル・認証方式

---

### 3. データモデル仕様書

**ファイル名パターン**: `database-schema.md`, `data-model.md`

**目的**: データ構造とエンティティ間の関係を定義

**必須記述項目**:
- エンティティ一覧
- 各エンティティのフィールド定義(名前、型、制約、説明)
- リレーションシップ(1対多、多対多等)
- インデックス設計
- 制約条件(UNIQUE, NOT NULL, CHECK等)
- マイグレーション方針

**AI実装に必要な情報**:
- 正規化レベルと理由
- NULL許容の判断基準
- デフォルト値の意図

---

### 4. API仕様書

**ファイル名パターン**: `api/{resource}.md` (例: `api/users.md`)

**目的**: REST APIまたはGraphQL APIの詳細を定義

**必須記述項目**:

#### 共通項目(REST/GraphQL共通)
- API種別(REST/GraphQL)
- 認証・認可要件
- レート制限
- バリデーション詳細:
  - フロントエンド責務(形式チェック、即時フィードバック)
  - バックエンド責務(ビジネスルール、データ整合性)
  - バリデーションエラーのレスポンス形式
  - エラーメッセージ(ユーザー向け表示文言)
- エラーレスポンス形式

#### REST API固有
- エンドポイント一覧
- 各エンドポイントの詳細:
  - HTTPメソッド
  - パス
  - リクエストパラメータ(パス/クエリ/ボディ)
  - リクエストボディの型定義
  - レスポンスボディの型定義(成功時/エラー時)
  - ステータスコード一覧

#### GraphQL固有
- スキーマ定義:
  - Query/Mutation/Subscription一覧
  - 各操作の詳細(引数、戻り値の型定義)
  - カスタム型定義
  - インターフェース/ユニオン型
- Resolver仕様:
  - データ取得元
  - N+1問題対策(DataLoader等)
  - キャッシュ戦略
- エラーハンドリング:
  - エラーコード体系
  - エラーレスポンス構造(errors配列)
  - 部分的成功の扱い

**AI実装に必要な情報**:
- バリデーションルールと実装箇所(フロント/バックエンド)
- 非同期バリデーション(DB問い合わせ等)の有無
- 副作用の有無(冪等性)
- トランザクション境界
- ページネーション戦略(REST: offset/cursor、GraphQL: connection pattern)
- フィールドレベルの認可(GraphQL)

### 5. コンポーネント仕様書(フロントエンド)

**ファイル名パターン**: `frontend/components/{component-name}.md`

**目的**: 再利用可能なUIコンポーネントの振る舞いを定義

**必須記述項目**:
- コンポーネントの責務
- Props定義(型、デフォルト値、必須/任意)
- State定義(内部状態を持つ場合)
- イベントハンドラ一覧
- バリデーション(フォーム系コンポーネントの場合):
  - バリデーションルール
  - バリデーションタイミング(onChange/onBlur/onSubmit)
  - エラー表示方法
  - 非同期バリデーション(API呼び出し等)
- 使用例(コード)
- バリエーション(異なる状態での見た目)
- アクセシビリティ要件
- エラー状態の表示

**AI実装に必要な情報**:
- Props変更時の副作用
- 再レンダリング条件
- 依存する他コンポーネント

---

### 6. ページ仕様書(フロントエンド)

**ファイル名パターン**: `frontend/pages/{page-name}.md`

**目的**: ページ単位のUI構成とデータフローを定義

**必須記述項目**:
- ページの目的・役割
- URL(パスパラメータ、クエリパラメータ含む)
- レイアウト構成(ワイヤーフレームまたはテキスト記述)
- 使用コンポーネント一覧
- データ取得方法(API呼び出し)
- ユーザーアクション一覧とその結果
- フォームがある場合:
  - バリデーションルール一覧
  - バリデーションタイミング
  - サーバーサイドバリデーションとの連携
  - 送信前の最終チェック
- ページ遷移条件
- 権限要件
- ローディング状態/エラー状態の表示

**AI実装に必要な情報**:
- 初回レンダリング時のデータ取得タイミング
- 状態管理の方針
- エラーハンドリング戦略

---

### 7. ビジネスロジック仕様書(バックエンド)

**ファイル名パターン**: `backend/services/{service-name}.md`

**目的**: ビジネスルールとロジックを定義

**必須記述項目**:
- サービスの責務
- 提供する機能(メソッド)一覧
- 各メソッドの詳細:
  - 入力パラメータ
  - 出力(戻り値)
  - 前提条件
  - バリデーションルール:
    - ビジネスルール検証
    - データ整合性チェック
    - 外部システム制約
  - 処理フロー
  - 副作用(データベース更新、外部API呼び出し等)
  - 例外条件とエラーハンドリング
- 依存する他サービス/リポジトリ

**AI実装に必要な情報**:
- トランザクション境界
- リトライポリシー
- タイムアウト設定

### 8. 統合仕様書(フロント・バックエンド連携)

**ファイル名パターン**: `integration/api-contract.md`, `integration/{feature}-flow.md`

**目的**: フロントエンドとバックエンド間の契約と連携方法を定義

**必須記述項目**:
- エンドツーエンドのデータフロー
- API呼び出しタイミング
- バリデーション戦略:
  - フロント/バックエンドの責任分担
  - バリデーションエラーの統一形式
  - エラーメッセージの表示方針
- エラーハンドリング方針(どのレイヤーで何を処理するか)
- 認証トークンの扱い
- リトライ/タイムアウトポリシー
- 楽観的更新(Optimistic Update)の有無
- キャッシュ戦略

**AI実装に必要な情報**:
- 責任境界の明確化
- エラー時のユーザー体験
- パフォーマンス要件

### 9. 認証・認可仕様書

**必須記述項目**:
- 認証方式(JWT, セッション等)
- トークン発行・検証フロー
- トークン有効期限とリフレッシュ戦略
- ロール/権限の定義
- エンドポイントごとの認可要件
- パスワードポリシー
- セキュリティヘッダー

**AI実装に必要な情報**:
- トークン保存場所(Cookie, LocalStorage等)
- CSRF対策の有無
- 多要素認証の有無

**必須記述項目**:

- 入力データ
- 処理内容
- 出力データ/副作用
- 失敗時のリトライポリシー
- タイムアウト
- 監視項目(成功率、実行時間等)

**AI実装に必要な情報**:
- 冪等性の保証
- 並列実行の可否
- データ量の想定

## 仕様書作成ガイドライン

### 1. Frontmatterの管理
- 仕様書作成時: 必須メタデータをすべて記入
- 仕様書更新時: `version`と`updated`を必ず更新
- ブレイキングチェンジ: メジャーバージョンを上げる(1.x.x → 2.0.0)
- 後方互換の変更: マイナーバージョンを上げる(x.1.x → x.2.0)
- 軽微な修正: パッチバージョンを上げる(x.x.1 → x.x.2)

### 2. 更新タイミング
- 機能追加/変更時: 実装前に仕様書を更新
- バグ修正時: 仕様に起因する場合は仕様書も修正
- リファクタリング時: 外部仕様が変わらなければ更新不要

### 3. レビュープロセス
- 仕様書の変更はコードレビューと同じプロセスでレビュー
- 仕様書とコードの乖離が発覚した場合、仕様書を正とする

### 4. バージョン管理
- 仕様書もGit管理
- 破壊的変更はCHANGELOGに記録

### 5. AI実装時の活用方法
- AIに仕様書の該当セクションを渡してコード生成
- 生成されたコードが仕様を満たしているかレビュー
- 仕様の曖昧な部分はAIが質問できるよう明示的に記述

## 仕様書記述の良い例・悪い例

### 例1: API仕様書の記述

#### ❌ 悪い例（曖昧な記述）

```markdown
## POST /users

ユーザーを作成する

**リクエスト**:
- email
- name
- password

**レスポンス**:
成功したら200を返す
```

**問題点**:
- 型定義がない
- バリデーションルールが不明
- エラー時の動作が不明
- フロント/バックエンドの責任分担が不明確

#### ✅ 良い例（明示的な記述）

```yaml
---
type: api
title: ユーザー作成API
version: 1.0.0
updated: 2025-11-21
---

## POST /api/v1/users

### 概要
新規ユーザーを作成する

### リクエスト

**ボディ** (application/json): `CreateUserRequest`
- `email`: メールアドレス形式、必須
- `name`: 1-100文字、必須
- `password`: 8文字以上（英数字記号含む）、必須

### バリデーション責任分担

**フロントエンド**:
- 形式チェック（メール形式、文字数、パスワード複雑度）
- 即時フィードバック（onChange/onBlur）
- 必須項目チェック

**バックエンド**:
- メールアドレス重複チェック（DB問い合わせ）
- パスワードハッシュ化と保存
- ビジネスルール検証
- 最終的な形式検証

### レスポンス

**成功時** (201 Created): `UserResponse`
- `id`: ユーザーID
- `email`: メールアドレス
- `name`: ユーザー名
- `createdAt`: 作成日時（ISO 8601形式）

**エラー時** (400 Bad Request): `ErrorResponse`
- `error.code`: エラーコード（例: "VALIDATION_ERROR"）
- `error.message`: エラーメッセージ
- `error.details[]`: 詳細エラー情報（フィールド名とメッセージ）

**改善点**:
- 型定義が明確
- フロント/バックエンドのバリデーション責任が明示
- エラーレスポンスの構造が具体的
- 日付形式が明示（ISO 8601）

### 例2: コンポーネント仕様書の記述

#### ❌ 悪い例（不十分な情報）

```markdown
## Button コンポーネント

ボタンを表示するコンポーネント

**Props**:
- text
- onClick
```

**問題点**:
- 型定義がない
- デフォルト値が不明
- バリエーションが不明
- アクセシビリティ要件が欠如

#### ✅ 良い例（包括的な定義）

```yaml
---
type: component
title: Button コンポーネント仕様書
version: 1.0.0
updated: 2025-11-21
---

## Button コンポーネント

### 概要
**責務**: ユーザーアクションをトリガーするクリック可能なボタンを提供

### Props定義

`ButtonProps`インターフェース:

**必須Props:**
- `children`: ボタンテキストまたは子要素

**任意Props:**
- `variant`: 'primary' | 'secondary' | 'danger' (デフォルト: 'primary')
- `size`: 'sm' | 'md' | 'lg' (デフォルト: 'md')
- `disabled`: boolean (デフォルト: false)
- `loading`: boolean (デフォルト: false)
- `onClick`: クリックハンドラ関数
- `type`: 'button' | 'submit' | 'reset' (デフォルト: 'button')
- `ariaLabel`: スクリーンリーダー用ラベル

### アクセシビリティ要件
- `type`属性を設定
- `disabled`または`loading`時に無効化
- `aria-label`でラベルを提供
- `aria-busy`でローディング状態を示す

**改善点**:
- TypeScript型定義が明確
- デフォルト値が明示
- アクセシビリティ要件が含まれる
- 具体的な使用例が提示

### 例3: データモデル仕様書の記述

#### ❌ 悪い例（不明確な定義）

```markdown
## User テーブル

| カラム | 型 |
|-------|---|
| id | number |
| email | string |
| name | string |
```

**問題点**:
- NULL許容が不明
- 一意制約が不明
- デフォルト値が不明
- リレーションシップが不明

#### ✅ 良い例（詳細な定義）

```yaml
---
type: database-schema
title: Userテーブル仕様書
version: 1.0.0
updated: 2025-11-21
---

## User テーブル

### フィールド定義

| カラム | 型 | NULL許容 | デフォルト値 | 制約 | 説明 |
|-------|---|---------|------------|-----|------|
| id | UUID | NOT NULL | uuid_generate_v4() | PRIMARY KEY | ユーザーID |
| email | VARCHAR(255) | NOT NULL | - | UNIQUE | メールアドレス |
| name | VARCHAR(100) | NOT NULL | - | - | 氏名 |
