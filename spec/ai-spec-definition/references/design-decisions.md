# 仕様書レビューエージェント - 設計判断

このファイルは、仕様書レビューエージェント（ai-spec-reviewer）の設計判断を説明します。

## なぜカスタム実装なのか

このエージェントは、標準的なエージェントテンプレートを使用せず、仕様書レビューに特化したカスタム実装を採用しています。

### カスタム実装の理由

#### 1. 専門性の高いドメイン知識

- **11種類の仕様書種別それぞれに固有のチェック項目**:
  - overview / architecture / api / component / page
  - service / integration / auth / job / infrastructure
  - database-schema

- **共通チェック項目（4カテゴリ）**:
  - Frontmatter（type, title, version, updated）
  - 構造と形式（見出し階層、コードブロック）
  - 明示性（暗黙の前提、境界条件、依存関係）
  - 具体性（具体例、制約条件）

- **各項目の評価基準**:
  - 準拠 / 部分的準拠 / 未準拠
  - A-Fグレード算出ロジック
  - 優先度分類（Critical/High/Medium/Low）

これらの知識を標準テンプレートに当てはめるのは困難です。

#### 2. 複雑なワークフロー

- **6ステップの詳細なレビュー手順**:
  1. 準備（ファイル特定、リソース読み込み、種別確認）
  2. 共通チェック項目の評価
  3. 種別固有チェック項目の評価
  4. 総合評価とグレード算出
  5. レビューレポート作成
  6. レポート出力

- **各ステップでの検証・エラーハンドリング**
- **段階的な評価とグレード算出**
- **優先度別の改善タスク生成**

これらを標準フォーマットで表現すると可読性が低下します。

#### 3. レビュー品質の一貫性

- **客観的な評価基準の明示**:
  - 準拠率の計算式
  - A-Fグレードの定義
  - 優先度分類の基準

- **一貫した適用**:
  - すべての仕様書に同じ基準を適用
  - 評価者による差異を最小化

これらの基準を一貫して適用するための詳細な指示が必要です。

#### 4. エラーハンドリングの多様性

- **多様なエッジケース**:
  - ファイル不在
  - 種別不明
  - Frontmatter欠如
  - 複数種別混在
  - 長大な仕様書（1000行超）
  - 既存レポートファイルの存在

- **各ケースに対する具体的な対応手順**
- **ユーザーとのインタラクション方法**

標準テンプレートでは対応が難しいシナリオです。

---

## 標準テンプレートへの移行検討

以下の条件を満たす場合、標準テンプレートへの移行を検討すべきです。

### 移行の条件

#### 1. シンプル化の可能性

- 仕様書種別が3種類以下に削減された
- レビューワークフローが3ステップ以下に簡素化された
- チェック項目が20項目以下になった

#### 2. 再利用性の向上

- 他のドメイン（コードレビュー、ドキュメントレビュー）でも同じパターンが使える
- 複数のプロジェクトで共通的に使えるレビューフレームワークが確立した

#### 3. 保守性の問題

- カスタム実装が500行を超えて保守が困難になった
- 複数の担当者が編集する必要が出てきた

---

## 現在の判断

### 評価指標

- **ファイルサイズ**: 約300行（v2.0.0時点、Progressive Disclosure適用後）
- **専門性**: 非常に高い（11種類の仕様書種別）
- **再利用性**: 仕様書レビュー専用（他ドメインへの転用は難しい）

### 結論

**カスタム実装を継続**

理由:
1. Progressive Disclosure原則に従い、メインファイルを300行以下に削減
2. 詳細情報を外部ファイルに分離（references/）
3. 専門性が高く、標準テンプレートへの移行メリットが少ない
4. メンテナンス性が改善され、複数ファイル構成で保守しやすい

---

## メンテナンス方針

### 1. バージョン管理

**Frontmatterの `changelog` フィールドで変更履歴を管理:**

- **機能追加**: マイナーバージョンアップ（1.0.0 → 1.1.0）
  - 例: 新しい仕様書種別の追加
  - 例: 新しいチェック項目の追加

- **破壊的変更**: メジャーバージョンアップ（1.0.0 → 2.0.0）
  - 例: ワークフローの大幅な変更
  - 例: グレード算出ロジックの変更

- **バグ修正**: パッチバージョンアップ（1.0.0 → 1.0.1）
  - 例: エラーハンドリングの修正
  - 例: ドキュメントの誤字修正

### 2. ファイルサイズ管理

**現状評価（v2.0.0時点）:**

- エージェント本体（`ai-spec-reviewer.md`）: 約300行
- ワークフロー詳細（`reviewer-workflow-guide.md`）: 約450行
- 使用例（`reviewer-examples.md`）: 約250行
- エッジケース（`reviewer-edge-cases.md`）: 約200行
- 設計判断（`design-decisions.md`）: 約150行

**合計**: 約1350行（外部ファイルを含む）

**分割の評価基準:**

- エージェント本体が400行を超えた場合、再分割を検討
- 外部ファイルが500行を超えた場合、さらに分割
- 新しい機能追加でロジックが複雑化した場合、分割を検討

**分割後の構成案（必要に応じて）:**

```
skills/spec/ai-spec-definition/
├── agents/
│   └── ai-spec-reviewer.md (300行以下、メインエージェント定義)
├── references/
│   ├── spec-definition.md (既存)
│   ├── review-checklist.md (既存)
│   ├── reviewer-workflow-guide.md (ワークフロー詳細)
│   ├── reviewer-workflow-step1-3.md (将来的な分割: ステップ1-3)
│   ├── reviewer-workflow-step4-6.md (将来的な分割: ステップ4-6)
│   ├── reviewer-examples.md (使用例)
│   ├── reviewer-edge-cases.md (エラーハンドリング)
│   └── design-decisions.md (設計判断)
└── templates/
    └── review-report-template.md (既存)
```

**現時点の判断:**

- **分割不要**: 各ファイルは管理可能な範囲内
- 各ファイルの見出し構造が明確で、検索性が高い
- Progressive Disclosure原則に準拠している
- **再評価時期**: v2.5.0リリース時、またはメインファイルが400行に達した時

### 3. 定期レビュー

**3ヶ月ごとに実施:**

- 使用状況のレビュー
- 新しい仕様書種別の追加検討
- チェック項目の見直し
- レビュー品質基準の更新
- ユーザーフィードバックの反映

**レビュー項目:**

1. **エージェントの有効性**:
   - レビュー結果の品質
   - ユーザー満足度
   - 改善提案の実用性

2. **パフォーマンス**:
   - レビュー処理時間
   - 大規模ファイル（1000行超）への対応

3. **拡張性**:
   - 新しい仕様書種別への対応
   - チェック項目の追加・削除

4. **保守性**:
   - コードの可読性
   - ドキュメントの網羅性
   - エラーハンドリングの適切性

## Progressive Disclosure適用の記録

### v2.0.0での変更（2025-11-21）

**変更内容:**

1. **エージェント本体の削減**:
   - 変更前: 830行
   - 変更後: 約300行
   - 削減率: 約64%

2. **外部ファイルへの分離**:
   - `reviewer-workflow-guide.md`: ワークフロー詳細（450行）
   - `reviewer-examples.md`: 使用例（250行）
   - `reviewer-edge-cases.md`: エラーハンドリング（200行）
   - `design-decisions.md`: 設計判断（150行）

3. **参照の1階層化**:
   - メインファイル → 外部ファイル（1階層のみ）
   - 外部ファイル間の相互参照なし

**改善効果:**

- **可読性向上**: エージェント本体が簡潔になり、理解しやすくなった
- **メンテナンス性向上**: 各ファイルが独立しており、編集しやすい
- **検索性向上**: 必要な情報がどのファイルにあるか明確

**学んだ教訓:**

1. **早期のProgressive Disclosure適用が重要**:
   - 830行になってから分割するより、最初から外部ファイルを活用すべきだった

2. **外部ファイルの命名規則**:
   - `reviewer-` プレフィックスで統一し、関連性を明確にした

3. **参照パスの一貫性**:
   - すべての参照を `skills/spec/ai-spec-definition/references/` に統一
