# 仕様書レビューエージェント - エッジケース対応

このファイルは、仕様書レビューエージェント（ai-spec-reviewer）のエラーハンドリングとエッジケース対応を説明します。

## ファイルが見つからない場合

**エラーメッセージ:**
```
仕様書ファイルが見つかりません。

検索したパス: [パス]

以下を確認してください:
1. ファイルパスが正しいか
2. ファイルが存在するか
3. 読み取り権限があるか
```

**エージェントの対応:**
1. 指定されたパスでファイルを検索
2. 見つからない場合、一般的な場所を確認:
   - `./specs/`
   - `./docs/`
   - `./`
3. それでも見つからない場合、ユーザーに再確認を求める

---

## 種別が不明な場合

**エラーメッセージ:**
```
仕様書の種別（type）が不明です。

現在のtype: [値]

対応できる種別:
- overview / architecture / api / component / page
- service / integration / auth / job / infrastructure
- database-schema

共通チェック項目のみでレビューを続行しますか？
```

**エージェントの対応:**
1. Frontmatterから `type` を読み取る
2. 11種類のいずれにも該当しない場合、ユーザーに確認:
   - 共通チェック項目のみでレビュー継続
   - または、内容から種別を推測してレビュー
3. ユーザーの選択に従って処理を進める

---

## テンプレートが見つからない場合

**エラーメッセージ:**
```
レビューレポートテンプレートが見つかりません。

検索したパス: skills/spec/ai-spec-definition/templates/review-report-template.md

デフォルトのレポート構造でレビューレポートを作成します。
```

**エージェントの対応:**
1. テンプレートファイルの存在を確認
2. 見つからない場合、デフォルトの構造でレポートを作成:
   - エグゼクティブサマリー
   - 詳細評価
   - 優先度別改善タスク
   - 具体的な修正例

---

## Frontmatterが完全に欠如している場合

**エラーメッセージ:**
```
仕様書にFrontmatterがありません。

現在の仕様書:
# タイトル
本文...

以下の情報をユーザーに確認してください:
1. 仕様書の種別（type）は何ですか？
   - 選択肢: overview / architecture / api / component / page / service / integration / auth / job / infrastructure / database-schema
2. バージョン番号（version）は何ですか？（推奨: 1.0.0）
3. 最終更新日（updated）はいつですか？（推奨: 今日の日付）

情報が提供されたら、Frontmatterを追加した上でレビューを続行します。
または、仮のFrontmatterを追加してレビューすることも可能です。
```

**エージェントの対応例:**

```
ユーザー: specs/payment.md をレビューしてください

エージェント:
1. ファイルを読み込み
2. Frontmatterが存在しないことを検出
3. ユーザーに確認:
   「この仕様書にはFrontmatterがありません。
   以下の情報を教えてください:
   1. 種別（type）: api / component / page など
   2. バージョン（version）: 例 1.0.0
   3. 最終更新日（updated）: 例 2025-11-21

   または、内容から推測してレビューを続行しますか？」

ユーザー: 内容から推測して続行してください

エージェント:
4. 内容を分析し、type: api と推測
5. 仮のFrontmatter情報でレビュー続行
6. レビューレポートに「Frontmatter欠如」をCritical問題として記載
```

---

## 複数の仕様書種別が混在している場合

**エラーメッセージ:**
```
この仕様書には複数の種別の内容が含まれています。

検出された内容:
- API仕様（エンドポイント定義）
- データモデル仕様（テーブル定義）
- ビジネスロジック仕様（サービスクラス）

推奨される対応:
1. 仕様書を複数ファイルに分割
   - user-api.md (API仕様)
   - user-model.md (データモデル)
   - user-service.md (ビジネスロジック)

2. または、現在のtype（例: api）を優先してレビュー
   - 他の種別の内容は「範囲外」として指摘

どちらの方法でレビューを続行しますか？
```

**エージェントの対応例:**

```
ユーザー: specs/user-management.md をレビューしてください

エージェント:
1. ファイルを読み込み（type: api）
2. 内容を分析
   - API仕様セクション（50%）
   - データモデルセクション（30%）
   - ビジネスロジックセクション（20%）
3. 複数種別混在を検出
4. ユーザーに確認:
   「この仕様書には複数の種別（API、データモデル、ビジネスロジック）が混在しています。

   推奨: 3つのファイルに分割
   - user-api.md
   - user-model.md
   - user-service.md

   または、API仕様として優先的にレビューを続行しますか？」

ユーザー: ファイル分割を推奨する形でレビューしてください

エージェント:
5. API仕様としてレビュー
6. レビューレポートに「ファイル分割推奨」をHigh問題として記載
```

## 非常に長い仕様書（1000行以上）の場合

**警告メッセージ:**
```
この仕様書は[行数]行と非常に長大です。

推奨される対応:
1. セクション分割してレビュー
   - Frontmatter + 序盤（1-300行）
   - 中盤（301-600行）
   - 終盤（601-終わり）

2. レビューレポートに「ファイル分割推奨」を明記

3. 各セクションの評価を統合して総合評価を算出

処理時間: 通常の2-3倍を想定
```

**エージェントの対応例:**

```
ユーザー: specs/comprehensive-api.md (1500行) をレビューしてください

エージェント:
1. ファイルサイズを確認（1500行）
2. ユーザーに通知:
   「この仕様書は1500行と長大です。
   セクション分割してレビューを実施します。
   処理時間は通常の3倍程度かかる見込みです。」

3. セクション1（1-500行）をレビュー
   - Frontmatter: ✓
   - 構造: △（見出しレベルスキップあり）

4. セクション2（501-1000行）をレビュー
   - API定義: ✓
   - 型定義: △（一部欠落）

5. セクション3（1001-1500行）をレビュー
   - エラーハンドリング: ✗（詳細不足）

6. 総合評価を算出（各セクションの平均）

7. レビューレポートに以下を記載:
   - High問題: 「1500行と長大すぎる。以下のように分割推奨:
     - user-api.md (ユーザー管理API)
     - product-api.md (商品管理API)
     - order-api.md (注文管理API)」
```

## 既存のレビューレポートファイルが存在する場合

**警告メッセージ:**
```
レビューレポートファイルが既に存在します。

既存ファイル: [パス]

以下のオプションを選択してください:
1. 上書きする（既存のレポートは失われます）
2. バックアップを作成して上書き（既存ファイルを [パス].backup にリネーム）
3. 新しいファイル名で保存（例: [パス]-2.md）
4. キャンセル
```

**エージェントの対応:**
1. 既存ファイルの存在を確認
2. ユーザーに選択肢を提示
3. ユーザーの選択に従って処理:
   - オプション1: 直接上書き
   - オプション2: 既存ファイルをリネーム後、新規作成
   - オプション3: 新しいファイル名で保存
   - オプション4: レビュー中止

---

## 仕様書の文字エンコーディングが不正な場合

**エラーメッセージ:**
```
仕様書ファイルの文字エンコーディングが正しくありません。

検出されたエンコーディング: [エンコーディング名]

UTF-8形式で保存し直してから、再度レビューを実行してください。
```

**エージェントの対応:**
1. ファイルのエンコーディングを検出
2. UTF-8以外の場合、エラーメッセージを表示
3. レビューを中止

---

## 権限エラー（読み取り・書き込み権限がない場合）

**エラーメッセージ:**
```
ファイルへのアクセス権限がありません。

対象ファイル: [パス]
エラー種別: [読み取り / 書き込み]

以下を確認してください:
1. ファイルの権限設定
2. ディレクトリの権限設定
3. 実行ユーザーの権限
```

**エージェントの対応:**
1. 権限エラーをキャッチ
2. ユーザーに詳細なエラーメッセージを表示
3. レビューを中止

## 一般的なトラブルシューティング

### チェック項目が評価できない場合

**対応:**
1. 欠落している情報を特定
2. レビューレポートに「情報不足」として記載
3. 評価可能な項目のみでレビューを継続
4. 準拠率計算から除外

### 参照ファイルが見つからない場合

**対応:**
1. `spec-definition.md` または `review-checklist.md` が見つからない
2. 一般的なチェック項目（Frontmatter、構造、明示性、具体性）のみでレビュー
3. ユーザーに参照ファイルの欠如を通知
4. 可能な範囲でレビューを継続

### レビュー中に予期しないエラーが発生した場合

**対応:**
1. エラーをキャッチして詳細をログに記録
2. ユーザーに分かりやすいエラーメッセージを表示
3. 可能であれば部分的なレビュー結果を保存
4. 回復可能な場合は処理を再試行

---

## エッジケース対応の原則

### 1. ユーザーに選択肢を提供
問題が発生した場合、可能な限りユーザーに選択肢を提示し、処理を継続できるようにする。

### 2. 部分的な成果を保存
完全なレビューができなくても、評価済みの項目については結果を保存する。

### 3. 明確なエラーメッセージ
エラー発生時は、原因と対処方法を具体的に説明する。

### 4. グレースフルデグレード
理想的な条件が満たされない場合でも、可能な範囲で機能を提供する。

### 5. ユーザーの判断を尊重
自動的に決定するのではなく、重要な判断はユーザーに委ねる。
