# 仕様書レビューエージェント - 使用例

このファイルは、仕様書レビューエージェント（ai-spec-reviewer）の使用例を提供します。

## 基本的な使用例

### 例1: 単一の仕様書をレビュー

**入力:**
```
ユーザー: specs/user-api.md の仕様書をレビューしてください
```

**エージェントの処理:**
1. `specs/user-api.md` を読み込み
2. `type: api` を確認
3. 共通チェック + API仕様書固有チェックを実施
4. 評価: B (75%準拠)
5. レビューレポートを `specs/user-api-review-report.md` に出力

**出力サマリー:**
```
レビュー完了！

総合評価: B (良好)
準拠率: 75%

Critical問題: 0件
High問題: 3件
Medium問題: 5件
Low問題: 2件

詳細はレビューレポートをご確認ください:
specs/user-api-review-report.md
```

---

### 例2: カスタムレポートパス指定

**入力:**
```
ユーザー: specs/button-component.md をレビューして、レポートは reviews/ に保存
```

**エージェントの処理:**
1. `specs/button-component.md` を読み込み
2. `type: component` を確認
3. コンポーネント仕様書のチェックを実施
4. レビューレポートを `reviews/button-component-review-report.md` に保存

## 完全なレビュー例: 問題がある仕様書のレビュー

### 入力仕様書（specs/user-registration-api.md）

```markdown
---
type: api
title: ユーザー登録API
---

# ユーザー登録API

## エンドポイント

POST /api/users

## リクエスト

- email: メールアドレス
- password: パスワード
- name: 名前

## レスポンス

成功したらユーザー情報を返す。
エラーの場合はエラーメッセージを返す。
```

### レビュー実行

**入力:**
```
ユーザー: specs/user-registration-api.md をレビューしてください
```

**エージェントの処理:**
1. 仕様書を読み込み
2. `type: api` を確認
3. チェック実施
   - Frontmatter: `version`, `updated` フィールドが不足 (✗)
   - 構造: 見出し階層は適切だが、型定義がない (△)
   - 明示性: 認証要件が不明、バリデーション責任分担が不明 (✗)
   - 具体性: 型定義がない、制約条件が曖昧 (✗)
   - API固有: ステータスコードが不明、エラー形式が不明 (✗)
4. 評価: D (35%準拠)
5. レビューレポート生成

### 出力レビューレポート（specs/user-registration-api-review-report.md）

```markdown
# 仕様書レビューレポート

**仕様書名**: ユーザー登録API
**種別**: api
**レビュー実施日**: 2025-11-21

## エグゼクティブサマリー

### 総合評価

- **評価グレード**: D
- **準拠率**: 35%
- **Critical問題**: 2件
- **High問題**: 4件
- **Medium問題**: 2件

### 主要な発見事項

**強み**:
1. API種別（REST）が明示されている
2. 基本的なエンドポイント情報が記載されている
3. 見出し階層が適切

**改善が必要な点**:
1. バージョン管理情報（version, updated）が欠如
2. 型定義が完全に欠落
3. バリデーション責任分担が不明確
4. エラーハンドリングの詳細が不足

## 優先度別改善タスク

### 🔴 Critical（即時対応が必要）

- [ ] **Frontmatterにバージョン情報を追加**
  - **問題**: version, updatedフィールドがなく、変更追跡ができない
  - **影響**: 仕様書の世代管理ができず、古い情報が使われるリスク
  - **修正案**:
    ```yaml
    ---
    type: api
    title: ユーザー登録API
    version: 1.0.0
    updated: 2025-11-21
    ---
    ```

- [ ] **型定義を追加**
  - **問題**: リクエスト・レスポンスに型定義がない
  - **影響**: AIが正確な実装コードを生成できない
  - **修正案**: `UserRegistrationRequest` と `UserRegistrationResponse` インターフェースを定義
    - リクエスト: `email`（メールアドレス）、`password`（8-100文字、英数字+記号）、`name`（1-50文字）
    - レスポンス: `id`、`email`、`name`、`createdAt`（ISO 8601形式）

### 🟠 High（優先的に対応すべき）

- [ ] **バリデーション責任分担を明記**
  - **修正案**:
    ```markdown
    ### バリデーション責任分担

    **フロントエンド**:
    - メール形式チェック（正規表現）
    - パスワード文字数・複雑度チェック
    - 名前文字数チェック（1-50文字）

    **バックエンド**:
    - メールアドレス重複チェック（DB問い合わせ）
    - パスワードハッシュ化（bcrypt）
    - すべてのバリデーションルールの最終検証
    ```

- [ ] **ステータスコード一覧を追加**
  - **修正案**:
    ```markdown
    ### ステータスコード

    - 201 Created: ユーザー登録成功
    - 400 Bad Request: バリデーションエラー
    - 409 Conflict: メールアドレス重複
    - 500 Internal Server Error: サーバーエラー
    ```

## 具体的な修正例

### 例1: リクエスト定義の改善

#### 修正前
```markdown
## リクエスト

- email: メールアドレス
- password: パスワード
- name: 名前
```

#### 修正後
```markdown
## リクエスト

**型定義**: `UserRegistrationRequest`
- `email`: メールアドレス（例: user@example.com）
- `password`: 8-100文字、英数字+記号必須
- `name`: 1-50文字

**制約条件**:
- email: RFC 5322準拠のメールアドレス形式
- password: 最小8文字、最大100文字、英数字+記号を含む
- name: 1-50文字、空白のみは不可
```

#### 改善ポイント
- TypeScript風の型定義を追加
- 具体的な制約条件を明記
- 例や形式を追加
```

## 完全なレビュー例: 長大な仕様書（1000行超）のレビュー

**入力:**
```
ユーザー: specs/comprehensive-system-api.md (1200行) をレビューしてください
```

**エージェントの処理:**
1. ファイルサイズを確認（1200行）
2. ユーザーに通知:
   ```
   この仕様書は1200行と長大です。
   セクション分割してレビューを実施します。
   処理時間は通常の3倍程度かかる見込みです。
   ```
3. セクション1（1-500行）をレビュー
   - Frontmatter: ✓
   - 構造: △（見出しレベルスキップあり）
4. セクション2（501-1000行）をレビュー
   - API定義: ✓
   - 型定義: △（一部欠落）
5. セクション3（1001-1200行）をレビュー
   - エラーハンドリング: ✗（詳細不足）
6. 総合評価を算出（各セクションの平均）
7. レビューレポートに以下を記載:
   ```
   High問題: 「1200行と長大すぎる。以下のように分割推奨:
   - user-api.md (ユーザー管理API)
   - product-api.md (商品管理API)
   - order-api.md (注文管理API)」
   ```

## ファイルパス指定なしの場合

**入力:**
```
ユーザー: 仕様書をレビューしてください
```

**エージェントの処理:**
1. 現在のディレクトリから `*.md` ファイルを検索
2. 候補が複数ある場合、ユーザーに選択を求める:
   ```
   以下の仕様書ファイルが見つかりました:
   1. specs/user-api.md
   2. specs/product-api.md
   3. specs/order-api.md

   どのファイルをレビューしますか？番号で指定してください。
   ```
3. ユーザーの選択に基づいてレビューを実施

---

## 改善の継続

レビュー後、以下を推奨:

1. **Critical/High問題の即時対応**: 仕様書の機能を回復
2. **改善後の再レビュー**: 改善が適切か確認
3. **定期的なレビュー**: 3ヶ月ごとに品質チェック
4. **チーム共有**: レビュー結果を関係者と共有
