# Guarantee Interview — 裁定インタビュー

保証台帳へ「判断の出来事」を供給する手順である。実装から観測した振る舞いについて人間に一問し、その裁定を文書へ残すことで、台帳の出自ルールが要求する根拠を新しく作る。

## ① 位置づけ — 3段のうち裁定を担う

```
guarantee-ledger ⑩ 突合 ──観測──▶ guarantee-interview ──裁定──▶ 台帳
   （実装を読む）                     （人間に聞く）           （宣言する）
```

| 段 | 担当 |
|---|---|
| 観測 | `guarantee-ledger` ⑩ 段階 2 突合 |
| 裁定 | **本スキル** |
| 宣言 | `guarantee-ledger` ①〜⑨ + checker |

本スキルは裁定だけを担う。台帳の表書式・出自列の形式・checker の契約は `guarantee-ledger` が正本であり、ここでは重複して定義しない。

本文中の丸数字は、修飾が無ければ本スキルの節番号を指す。他スキルの節はスキル名を冠して書く（`guarantee-ledger` ⑩ 等）。**面**とは外部から観測できる単位（HTTP API・CLI 出力・スケジューラ・Webhook・画面等）であり、台帳が整理の単位とするものと同じである。

### 事後棚卸しとの違い

本機構は「実装から保証を起こす」ように見えるため、`guarantee-ledger` ⑧ が禁じた事後棚卸しの復活かという問いに必ず晒される。答えを設計の芯に置く。

> 観測は実装から来てよい。**昇格は今ここでの人間の裁定から来る。**

事後棚卸しが禁じられる理由は「実装が決めた振る舞いが、人間の判断を経ずに契約へ昇格する」ことである。人間の裁定を経る経路はその理由に抵触しない。過去の判断を捏造せず、現在の判断を新しく作る。

### 崩壊モード

本機構の失敗形は**ラバースタンプ**である。「これは意図どおりですね？」に yes を並べるだけの運用に落ちれば、出自の捏造装置となり、禁じたはずの事後棚卸しと同じものへ潰れる。以下の各節はすべてこの崩壊モードへの対策である。

## ② 入口

入口は 2 つ持つが、いずれも ④ の問いカードへ正規化してから同一の裁定ループへ入る。

| 入口 | 種 | 使う場面 |
|---|---|---|
| A（先行） | `guarantee-ledger` ⑩ 突合が出した `unrequested` / `partial` | 台帳が既にある面。材料が既に存在する |
| B | 面の walkthrough（形の正本・画面を見ながら順に問う） | 台帳がゼロの面。`guarantee-ledger` ⑩ を回す前のブートストラップ |

> **新しいキューを作らない。** 入口 A のキューは突合レポートそのものであり、入口 B は面の一覧がキューである。

入口 B は A との差分だけを持つ。④ 以降の問いカード・裁定ループ・記録・打ち切りは共通であり、B 固有なのは材料の出所だけである。B では形の正本と画面を**面の目次として**使い、そこに並ぶ操作を順に辿って、正本が定めていない振る舞いを拾う（正本が定めている事柄はそのまま ③ の条件 2 で落ちる）。B は A より根拠が薄いため（⑧ 参照）、初回は A で回す。

入口 A は突合レポートが item ごとの識別子を持ってリポジトリ内に残っていることを前提とする。会話の中だけに出力した突合結果はキューにならない。

## ③ 問いの門 — 何を問いにするか

次の 3 条件をすべて満たすものだけを問いにする。

1. **台帳がその振る舞いを約束していない**（該当行が無い、または既存行の保証文が当該の振る舞いを覆っていない）
2. **形の正本（OpenAPI・CLI ヘルプ・型定義等）を読んでも分からない**
3. 利用者から観測でき、壊れたら困る

条件 1 が「台帳に無い」でないのは、入口 A が `partial`（台帳に行はあるが保証文が実装の振る舞いを覆っていない）も材料に含むためである。行の有無で書くと partial が全件落ちる。**問うているのは行の有無ではなく約束の有無である。**

門は機械的であり、基準が明文である。判定に人間を呼ばない。この門を通らないものは問いにしない。条件 3 は、④ が要求する「壊れた場合に利用者へ起きること」を 1 文で書けるかで判定する。書けなければ通さない。

門で落とした item も裁定文書へ 1 行で列挙する（item の識別子と、満たさなかった条件の番号）。節は作らないが、⑦ の再開では決着済みとして扱いキューから外す。**どこにも記録せずに落とさない。**

## ④ 問いカード

エージェントは「実装はこうなっている」という事実だけを提示し、**推奨を述べない。**「意図的に見える」「妥当と思われる」といった評価語を含めない。

| | 内容 |
|---|---|
| 含める | 観測した振る舞い（**利用者から見た形**で書く。内部実装の用語で書かない） |
| 含める | その振る舞いが現れる操作・経路 |
| 含める | **観測の根拠** — 読んだ実装ファイルの該当箇所、または実際に動かした手順。形の正本については読んだ定義の箇所 |
| 含める | 形の正本がその点について何も言っていないことの確認結果 |
| 含める | 壊れた場合に利用者へ起きること |
| 含めない | 実装がそうなっている理由の推測 |
| 含めない | 他の選択肢の評価、エージェントの結論 |

> **技術的必然性の調査（「スキーマ制約上その選択肢しかない」等）を、問う前に行わない。** 人間が「非意図」と裁定すれば、その調査は不要になる。

禁じているのは *なぜそうなっているか* の掘り下げであり、観測の根拠として求める *どこを見てそう言っているか* の開示とは別物である。根拠が無い問いカードでは、人間は提示を信じる以外にできることがない。

## ⑤ 裁定ループ

人間へ問うのは「**意図か否か**」だけである。「保証に値するか」は ③ の門が既に判定しており、裁定の場で再度問わない。

| 裁定 | 意味 | 行き先 |
|---|---|---|
| **意図** | 意図どおり | **台帳へ**（`pin確認` は空欄で入る） |
| **非意図** | 意図していない | 修正をそのリポジトリの課題管理（Action・issue 等）へ積む。セキュリティに関わるもの（⑥ の列挙）は公開の課題管理へ再現経路・影響を書かず、⑥ と同じ非公開の追跡先へ積む。**現行挙動を台帳に載せない** |
| **保留** | 判断できない | 次回へ持ち越す |

裁定はこの 3 つに固定する。「約束だ」と「意図だが約束ではない」を対等に並べる形は採らない。同じ判断を二度させることになり、人間が「約束と呼ぶほどでは」で流せる逃げ道を作る。門を通った実害ある振る舞いが宙に消える、ラバースタンプの逆向きの失敗（取りこぼし）である。

台帳へ反映するときの分岐を 2 つ定める。

- **裏付けテストが無い item は、意図と裁定しても台帳へ載せない。** テスト作成を Action へ積み、テストが入ってから載せる（`guarantee-ledger` ⑥）。裁定文書の節は先に残るため、後から同じ出自を指して載せられる。ただし**後から載せるときは、台帳へ書く `保証` が裁定節に記録された振る舞いと一致することを確認する。** 実装が変わって一致しなくなっていたら、その節を出自にせず裁定し直す
- **`partial` を意図と裁定した場合は新しい行を起こさない。** 既存行の `保証` を実装の振る舞いへ合わせて正確にし（範囲を広げる、または成り立つ条件を明示する）、`出自` を裁定文書の該当節へ差し替える。非意図と裁定したなら実装を直す Action を積み、`保証` は維持する。**範囲を広げる書き換えでは、広げた部分を既存の `裏付けテスト` が覆っているかを確認する。** 覆っていなければ書き換えず、テスト追加を積んでから書き換える（新規行と同じ扱い）

`partial` で人間へ問う対象は「**実装の現在の振る舞いが意図どおりか**」である。書き換えの制約は 1 つだけ置く。

> **保証の核を弱めない。** 核ごと落とすのは退役であり、`guarantee-ledger` ③ の退役提案として扱う（本スキルの経路ではない）。

### 「非意図」が生命線である

既存アプリの仕様再確認は、保証だけでなく**バグと仕様漏れも掘り出す。** エージェントが指示の隙間を埋めた振る舞いは、正しく動いていても正しいとは限らない。この裁定を持たない機構は現状追認装置であり、誤った実装を契約へ昇格させる。

### 「保留」を正当な出口として置く

`guarantee-ledger` ①「迷ったら載せない」が既にこれを支持している。新ルールの発明ではなく、既存原則の適用である。保留を選びにくい場に作ると、判断できないものが追認へ流れる。

### 理由の一文を必須とする

人間の理由は**逐語で**残す。整形・要約・言い換えをしない。要約すると、後から読んだときに「エージェントが書いた理由」と区別できなくなり、`guarantee-ledger` ⑪ の形骸化判定にそのまま落ちる。

> **裁定者をエージェントで代理しない。** 他のエージェント（司令塔・サブエージェントを含む）の応答を人間の裁定として記録しない。

### 但し書き — 固定したくない場合

「意図どおりだが、近く変える／変える余地を残したい」場合は、意図と裁定したうえで台帳へは載せず、そのリポジトリのリスク記録（`risk-registry` 等）へ回す。

> **この理由に限定する。**「約束と呼ぶほどでは」は理由として認めない。**但し書きの発動は人間の発話に限る**——エージェントは適用を提案できるが、判定しない。

理由は逐語で裁定文書へ残す。リスク記録の置き場が無いリポジトリでは、裁定文書の当該節へ「台帳へ載せない理由」として残す。**どこにも記録せずに落とさない。**

選択肢として対等に並べず、理由を限定した脱出口として置くのは、逃げ道化を防ぐためである。台帳へ載せると、将来その振る舞いを改善する変更が保証違反になる——改善そのものを妨げる場合が該当する。

## ⑥ 記録

裁定文書を 1 本作る。パスはリポジトリルートからの相対で `.docs/reviews/YYYY-MM-DD-guarantee-interview-<面>.md`。**1 文書 = 1 セッション**とし、⑦ の打ち切り条件のいずれかを満たした時点、またはキューが尽きた時点でその文書は閉じる。

`<面>` は面を一意に指す小文字英数とハイフンの文字列とする。導出規則を置かず、**初回セッションで決めて裁定文書の冒頭へ `面: <台帳の面セクション見出し、または面の呼称> / スラッグ: <面>` を 1 行残す。** 2 回目以降は既存の裁定文書の冒頭宣言から引き継ぎ、決め直さない。台帳にその面のセクションがまだ無い場合（入口 B）も同じ扱いで、後にセクションを起こすときはこのスラッグと対応する見出しを付ける。同じ日・同じ面で 2 本目を起こす場合は**日付側へ連番を付ける**（`YYYY-MM-DD-2-guarantee-interview-<面>.md`）——面の側に付けると ⑦ の列挙から漏れる。**既存の裁定文書を上書き・改題しない。** 既に台帳の出自が指している。

- **すべての裁定を 1 件 = 1 節として記録する。** 意図・非意図・保留のいずれも節を持ち、但し書きでリスク記録へ回した item も節を持つ。各節に**裁定区分**と人間の理由を逐語で書く
- **節見出しの冒頭に、その item をキュー上で一意に指す識別子を置く**（入口 A は突合レポートの item 番号や台帳 ID、入口 B は面と観測対象を一意に指す短い語）。⑦ の再開はこの識別子で突合する
- 各節の冒頭に `裁定者: <人間の識別> / 裁定日: YYYY-MM-DD / 逐語確認: 済 YYYY-MM-DD` を置く。**裁定者にエージェント名を書かない**——書けない欄があることが代理の禁止を可視化する。逐語確認を得ていない節はこの記載を欠いたまま残り、出自にできない
- 台帳の出自になるのは意図と裁定した節だけである。節見出しがそのまま出自になる。出自列の形式と見出しに使えない文字（`|`）は `guarantee-ledger` ② が正本
- 裁定文書へ記入した内容、特に理由の逐語部分を**人間へ提示し、一致の確認を得てから台帳へ反映する**。提示はセッション終了時にまとめて行ってよい
- **非意図・保留のうちセキュリティに関わるもの**（認可・テナント分離・存在秘匿・秘密の露出）は、節へ再現経路と影響を書かない。節には裁定区分と非公開の追跡先への参照だけを置く。**理由の逐語が再現経路や影響を含む場合は、その逐語を追跡先へ逐語のまま移し、節には `[理由の逐語は <追跡先> へ移した]` と置換の事実を残す。** ⑤ の逐語規則への例外はこの置換に限り、黙って要約・削除しない。**節そのものは省略しない**（`guarantee-ledger` ⑪ の判定材料と ⑦ の決着判定が節の存在に依存するため）

台帳行を持たない裁定こそ `guarantee-ledger` ⑪ の判定材料であり、⑦ の再開位置でもある。記録を省くと裁定文書に追認だけが並び、同 ⑪ が健全な運用を形骸化と誤判定する。

順序を固定する。

> **会話 → 裁定文書へ記入 → 台帳へ反映。**

会話は揮発する。`guarantee-ledger` ②「文書に残らないやりとりは保証にできない」がそのまま効く。台帳へ先に書くと、出自が指す先が存在しない状態が生まれる。

反映の**前後**に `scripts/check-guarantees.sh` を実行し、次の 3 点を確認する（契約は `guarantee-ledger` ⑨）。`broken=0` だけを完了の根拠にしない——検査されずに読み飛ばされた行も `broken=0` を返す。

- `broken=0` である
- **新しい行を起こしたなら、`checked` が「起こした行数と同じだけ」増えている。** 1 本でも足りなければ、その行は ID の形式が不正で検査対象から外れている（前後とも `broken=0` なら差分は新規有効行の本数と一致する）
- **台帳へ書いた出自の `::` 以降が、裁定文書に見出しとして丸ごと実在する。** checker は見出しを検査しないため grep で照合する。照合する文字列は**台帳の行を `|` で列分割して得た `出自` セルから外側のバッククォートだけを外し、最初の `::` 以降を取ったもの**とする——書いたつもりの文字列で照合すると切り詰めを見逃し、見出し内のバッククォートまで落とすと正しい見出しが不一致になる。一致しなければ見出しに `|` が含まれて切り詰められている
- **その見出し直下に `裁定者 / 裁定日 / 逐語確認: 済` の 3 項が揃っている。** 欠けている節は出自にできない

`unpinned` が増えるのは正常——意図と裁定した item は `pin確認` 空欄で入る。裁定文書と台帳の更新は同一 PR に含める（`guarantee-ledger` ⑪ の判定者が全裁定を読めるようにするため）。ただし ⑤ によりテスト作成を待つ item は例外とし、**裁定文書だけを当該 PR に含める。** 台帳行は後続 PR で同じ節を出自として追加する。

## ⑦ 規模と打ち切り

問いカードは 1 枚ずつ提示し、裁定を受けてから次を出す。1 セッション **10 件**を上限とし、5 件を超えた時点で続行するかを人間へ確認する。打ち切り条件は次の 3 つ。

- 件数上限に達した（または 5 件超で人間が続行しないと答えた）
- 人間が止めた
- **保留が 3 連続した**（提示が悪いか人間が疲れている。いずれもその日の続行に意味がない。連続のカウントはセッションごとにリセットする）
- キューが尽きた（決着済みを除いた残りが 0 件になった。これが正常終了である）

意図と非意図と門落ちを決着済み、保留を未決着として扱う。**保留も節を残したうえでキューに残す。** 再開時は同じ面の既存 `.docs/reviews/*-guarantee-interview-<面>.md` を列挙し、**⑥ の節見出しと ③ の門落ち列挙の双方の識別子で**突合して決着済みの item を除いた残りをキューとする（冪等・再開可能）。キューは突合レポートであり消えない。

保留した item は、提示を作り直す（利用者から見た形・影響の書き直し、形の正本の再確認）まで再提示しない。**作り直すまでは提示の対象にしないだけで、キューからは外さない**——未決着のまま追跡し続ける。

`guarantee-ledger` ⑩ 突合は網羅的に読み合わせること自体に価値があるため途中で止めにくいが、本機構は逆に積極的に打ち切ってよい。1 件ごとに独立した価値が出るため、途中で止めても成果が残る。

## ⑧ 成熟度

> **本手順は 2026-08-17 時点でまだ一度も実施されていない（n=0）。**

本手順は manako の 1 回の突合（2026-08-17、`unrequested` 11 件検出）と 3 件の裁定から起こしたものであり、インタビュー形式そのものは未実施である。初回実施の結果で改訂する前提とする。特に次の項目は根拠が薄い。

| 項目 | 状態 |
|---|---|
| 入口 B（面の walkthrough） | A より根拠が薄い。初回は A で回し、結果を見て改訂する |
| 1 セッションの件数上限（⑦） | 実測に基づかない。初回で実際の疲労点を測る |
| 保留 3 連続という打ち切り線 | 同上 |
| 保留 item の再提示条件（提示の作り直し） | 未観測。同一 item が回を跨いで保留を繰り返すかを初回で測る |

設計の全文は正本リポジトリ `elchika-inc/agent-toolkit` の `.docs/plans/guarantee-interview-skill-design.md` にある（配布先には存在しない。本スキルの実行には不要）。
