# 仕様書レビューエージェント - ワークフロー詳細ガイド

このファイルは、仕様書レビューエージェント（ai-spec-reviewer）の6ステップのレビューワークフローを詳細に説明します。

## レビュー実施手順（詳細版）

### ステップ1: 準備

#### 1.1 仕様書ファイルの特定

**アクション:**
- ユーザーから仕様書のパスを受け取る
- パスが指定されていない場合、現在のディレクトリから `*.md` ファイルを検索
- 候補が複数ある場合、ユーザーに選択を求める

**検証:**
- ファイルが存在するか確認
- 読み取り権限があるか確認
- ファイル形式が `.md` か確認

**エラーハンドリング:**
- ファイルが見つからない場合:
  1. 一般的な場所（`./specs/`, `./docs/`, `./`）を検索
  2. それでも見つからない場合、ユーザーに再確認
  3. 詳細なエラーメッセージを表示（`references/reviewer-edge-cases.md` 参照）

#### 1.2 必要なリソースの読み込み

**読み込むファイル:**
1. 対象仕様書
2. `skills/spec/ai-spec-definition/references/spec-definition.md`
3. `skills/spec/ai-spec-definition/references/review-checklist.md`
4. `skills/spec/ai-spec-definition/templates/review-report-template.md`

**検証:**
- すべてのファイルが正常に読み込めたか確認
- 参照ファイルが見つからない場合でも、基本的なチェック項目でレビュー継続

**エラーハンドリング:**
- 参照ファイルが見つからない場合:
  1. ユーザーに通知
  2. 基本的なチェック項目（Frontmatter、構造、明示性、具体性）でレビュー継続
  3. レビューレポートに参照ファイル欠如を記載

#### 1.3 仕様書種別の確認

**アクション:**
- Frontmatterから `type` フィールドを抽出
- 11種類のいずれかに該当するか確認:
  - `overview` / `architecture` / `api` / `component` / `page`
  - `service` / `integration` / `auth` / `job`
  - `infrastructure` / `database-schema`

**検証:**
- `type` フィールドが存在するか
- 値が有効な種別か

**エラーハンドリング:**
- `type` が存在しない、または無効な場合:
  1. 内容から種別を推測
  2. ユーザーに確認を求める
  3. 共通チェック項目のみでレビュー継続

### ステップ2: 共通チェック項目の評価

すべての仕様書に適用される共通のチェック項目を評価します。

#### 2.1 Frontmatterのチェック

**チェック項目:**
- [ ] `type` フィールドが存在し、有効な値か
- [ ] `title` フィールドが存在し、説明的か
- [ ] `version` フィールドが存在し、セマンティックバージョニング形式か（例: 1.0.0）
- [ ] `updated` フィールドが存在し、ISO 8601形式か（例: 2025-11-21）

**評価基準:**
- **準拠**: すべての必須フィールドが存在し、正しい形式
- **部分的準拠**: 一部のフィールドが欠落または形式が不適切
- **未準拠**: 複数のフィールドが欠落または形式が不適切

**検証:**
- Frontmatterが存在するか
- 各フィールドの形式が正しいか

**エラーハンドリング:**
- Frontmatterが完全に欠如している場合: `references/reviewer-edge-cases.md` を参照

#### 2.2 構造と形式のチェック

**チェック項目:**
- [ ] 見出し階層が適切か（`#` はタイトルのみ、本文は `##` から）
- [ ] 見出しレベルのスキップがないか（`##` から `####` へのジャンプなど）
- [ ] コードブロックに言語指定があるか（\`\`\`typescript、\`\`\`json など）
- [ ] 型定義がTypeScript風記法で記述されているか（`interface`, `type` など）

**評価基準:**
- **準拠**: すべての構造と形式が適切
- **部分的準拠**: 一部の見出しやコードブロックに問題
- **未準拠**: 構造が混乱している、または多くの形式エラー

**検証:**
- マークダウン構文が正しいか
- 見出し階層に論理的な流れがあるか

#### 2.3 明示性のチェック

**チェック項目:**
- [ ] 暗黙の前提がないか（「当然」「明らか」といった表現を避ける）
- [ ] 境界条件（正常系・エラーケース）が記述されているか
- [ ] 依存関係が明示されているか（使用するライブラリ、APIなど）

**評価基準:**
- **準拠**: すべての前提、境界条件、依存関係が明示されている
- **部分的準拠**: 一部が明示されているが、欠落がある
- **未準拠**: 多くの情報が暗黙的で不明確

**検証:**
- すべての動作が明示的に説明されているか
- 読者が推測する必要がないか

#### 2.4 具体性のチェック

**チェック項目:**
- [ ] 具体例が含まれているか（リクエスト/レスポンスの例、使用例など）
- [ ] 制約条件が具体的か（「短い」ではなく「1-100文字」）

**評価基準:**
- **準拠**: 十分な具体例があり、すべての制約が数値化されている
- **部分的準拠**: 一部の具体例や制約が不足
- **未準拠**: 抽象的な説明が多く、具体例が少ない

**検証:**
- 各セクションに具体例があるか
- 制約条件が測定可能な形で表現されているか

### ステップ3: 種別固有チェック項目の評価

仕様書種別に応じたチェック項目を評価します。

#### API仕様書（type: api）のチェック項目

- [ ] API種別（REST/GraphQL）が明記されているか
- [ ] 認証・認可要件が記述されているか
- [ ] フロント/バックエンドのバリデーション責任分担が明確か
- [ ] エンドポイント一覧またはスキーマ定義が存在するか
- [ ] リクエスト・レスポンスの型定義が存在するか
- [ ] エラーレスポンス形式が定義されているか
- [ ] ステータスコード一覧が記載されているか（REST）
- [ ] Resolver仕様が記述されているか（GraphQL）

#### コンポーネント仕様書（type: component）のチェック項目

- [ ] コンポーネントの責務が明確か
- [ ] Props定義が完全か（型、必須/任意、デフォルト値）
- [ ] 使用例が含まれているか
- [ ] ARIA属性が定義されているか（アクセシビリティ）
- [ ] キーボード操作が定義されているか
- [ ] スクリーンリーダー対応が考慮されているか
- [ ] バリデーションルールが定義されているか（フォーム系）

#### ページ仕様書（type: page）のチェック項目

- [ ] ページの目的が明確か
- [ ] URLとパラメータが定義されているか
- [ ] 使用コンポーネント一覧が存在するか
- [ ] データ取得方法が明記されているか（API呼び出し、SSR、SSGなど）
- [ ] ユーザーアクションと結果が定義されているか
- [ ] フォームフィールド一覧が存在するか（フォームがある場合）
- [ ] バリデーション責任分担が明確か
- [ ] ローディング状態が定義されているか
- [ ] エラー状態が定義されているか

#### データモデル仕様書（type: database-schema）のチェック項目

- [ ] エンティティ一覧が存在するか
- [ ] フィールド定義が完全か（型、NULL許容、デフォルト値、制約）
- [ ] リレーションシップが明記されているか（1:1、1:N、N:Nなど）
- [ ] インデックスが定義されているか
- [ ] 一意制約が明確か
- [ ] マイグレーション方針が記述されているか

#### ビジネスロジック仕様書（type: service）のチェック項目

- [ ] サービスの責務が明確か
- [ ] 提供機能一覧が存在するか
- [ ] 各メソッドの詳細が記述されているか（引数、戻り値、副作用）
- [ ] ビジネスルール検証が明記されているか
- [ ] トランザクション境界が明確か
- [ ] ロールバック条件が定義されているか

**詳細なチェック項目は `references/review-checklist.md` を参照してください。**

### ステップ4: 総合評価とグレード算出

#### 4.1 準拠率の計算

**計算式:**
```
準拠率 = (準拠項目数 + 部分的準拠項目数 × 0.5) / 総チェック項目数 × 100
```

**例:**
- 総チェック項目数: 20項目
- 準拠: 10項目
- 部分的準拠: 6項目
- 未準拠: 4項目

```
準拠率 = (10 + 6 × 0.5) / 20 × 100 = 65%
```

#### 4.2 総合評価グレードの算出

**グレード基準:**
- **A**: 90%以上準拠（優秀） - 実装に適した高品質な仕様書
- **B**: 70-89%準拠（良好） - 軽微な改善で実装可能
- **C**: 50-69%準拠（普通） - いくつかの重要な改善が必要
- **D**: 30-49%準拠（不十分） - 多くの改善が必要
- **F**: 30%未満準拠（不合格） - 大幅な書き直しが必要

#### 4.3 問題の優先度分類

各問題を以下の優先度に分類:

**Critical（🔴）**: 即時対応が必要
- 仕様書が機能しない（Frontmatter欠如、型定義完全欠落など）
- AIが実装できない致命的な情報不足
- 影響範囲が広く、プロジェクト全体に波及する問題

**High（🟠）**: 優先的に対応すべき
- AI実装時の誤解を招く曖昧な記述
- 重要な情報が欠落（認証要件、バリデーション責任など）
- 影響範囲が中程度の問題

**Medium（🟡）**: 計画的に対応
- 品質向上に繋がる改善（具体例の追加、制約条件の明確化）
- 影響範囲が限定的な問題

**Low（🟢）**: 将来的な改善
- より良い仕様書にするための推奨事項
- 影響が小さい形式的な問題

### ステップ5: レビューレポート作成

#### 5.1 テンプレートの読み込み

`templates/review-report-template.md` をベースにレポートを作成します。

**テンプレートが見つからない場合:**
デフォルトの構造でレポートを作成（`references/reviewer-edge-cases.md` 参照）。

#### 5.2 必須セクションの作成

##### (1) エグゼクティブサマリー

**含める内容:**
- 総合評価グレード（A-F）と準拠率（%）
- Critical/High/Medium/Lowの問題数
- 主要な発見事項:
  - 強み3つ（良い点）
  - 改善が必要な点3つ（優先度の高い問題）

**例:**
```markdown
## エグゼクティブサマリー

### 総合評価

- **評価グレード**: B
- **準拠率**: 75%
- **Critical問題**: 0件
- **High問題**: 3件
- **Medium問題**: 5件
- **Low問題**: 2件

### 主要な発見事項

**強み**:
1. API種別（REST）が明示されている
2. 基本的なエンドポイント情報が記載されている
3. 見出し階層が適切

**改善が必要な点**:
1. バージョン管理情報（version, updated）が欠如
2. 型定義が一部欠落
3. バリデーション責任分担が不明確
```

##### (2) 詳細評価

共通チェック項目と種別固有チェック項目の評価結果を表形式で記載:

**例:**
```markdown
## 詳細評価

### 共通チェック項目

| 項目 | 評価 | 備考 |
|------|------|------|
| Frontmatter | △ 部分的準拠 | version, updated フィールドが不足 |
| 構造と形式 | ✓ 準拠 | 見出し階層、コードブロックが適切 |
| 明示性 | △ 部分的準拠 | 認証要件が不明 |
| 具体性 | ✗ 未準拠 | 型定義が不足、制約条件が曖昧 |

### API仕様書固有チェック項目

| 項目 | 評価 | 備考 |
|------|------|------|
| API種別 | ✓ 準拠 | REST APIとして明記 |
| 認証・認可 | ✗ 未準拠 | 要件が記述されていない |
| エンドポイント一覧 | ✓ 準拠 | 全エンドポイントが記載 |
| 型定義 | △ 部分的準拠 | リクエストは定義済、レスポンスが不足 |
```

##### (3) 優先度別改善タスク

Critical/High/Medium/Low ごとにタスクリストを作成:

**各タスクに含める情報:**
- 問題の内容
- 影響
- 修正案（具体的なコード例を含む）
- 参照箇所（行番号またはセクション名）

**例:**
```markdown
## 優先度別改善タスク

### 🔴 Critical（即時対応が必要）

- [ ] **Frontmatterにバージョン情報を追加**
  - **問題**: version, updatedフィールドがなく、変更追跡ができない
  - **影響**: 仕様書の世代管理ができず、古い情報が使われるリスク
  - **参照**: 1-5行目
  - **修正案**:
    \```yaml
    ---
    type: api
    title: ユーザー登録API
    version: 1.0.0
    updated: 2025-11-21
    ---
    \```
```

##### (4) 具体的な修正例

少なくとも3つの修正例を提示:
- 修正前/修正後の対比
- 改善ポイントの説明

##### (5) 改善実施プラン

**Phase 1（緊急対応）**: Critical問題
**Phase 2（重要な改善）**: High問題
**Phase 3（品質向上）**: Medium問題

#### 5.3 レポート作成時の注意点

- **具体的であること**: 「改善が必要」だけでなく「どう改善するか」を明示
- **実行可能であること**: すぐに実装できる具体的な提案
- **バランスが取れていること**: 良い点も記載してモチベーション維持
- **優先度が明確であること**: 何から着手すべきか明確に

### ステップ6: レポート出力

#### 6.1 レポートファイルの保存

**デフォルトパス:**
```
[仕様書名]-review-report.md
```

**例:**
- 仕様書: `specs/user-api.md`
- レポート: `specs/user-api-review-report.md`

**ユーザー指定がある場合:**
ユーザーが指定したパスに保存

**既存ファイルの扱い:**
既存のレビューレポートファイルが存在する場合、ユーザーに確認
（`references/reviewer-edge-cases.md` 参照）

#### 6.2 サマリーの表示

レポート保存後、以下のサマリーを表示:

```
レビュー完了！

総合評価: B (良好)
準拠率: 75%

Critical問題: 0件
High問題: 3件
Medium問題: 5件
Low問題: 2件

詳細はレビューレポートをご確認ください:
[ファイルパス]
```

## ワークフロー全体のフローチャート

```
[ステップ1: 準備]
  ↓
  ├─ 仕様書ファイルを特定
  ├─ 必要なリソースを読み込み
  └─ 仕様書種別を確認
  ↓
[ステップ2: 共通チェック項目の評価]
  ↓
  ├─ Frontmatterチェック
  ├─ 構造と形式チェック
  ├─ 明示性チェック
  └─ 具体性チェック
  ↓
[ステップ3: 種別固有チェック項目の評価]
  ↓
  └─ API / Component / Page / など種別に応じたチェック
  ↓
[ステップ4: 総合評価とグレード算出]
  ↓
  ├─ 準拠率を計算
  ├─ 総合評価グレードを算出（A-F）
  └─ 問題を優先度分類（Critical/High/Medium/Low）
  ↓
[ステップ5: レビューレポート作成]
  ↓
  ├─ エグゼクティブサマリー
  ├─ 詳細評価
  ├─ 優先度別改善タスク
  ├─ 具体的な修正例
  └─ 改善実施プラン
  ↓
[ステップ6: レポート出力]
  ↓
  ├─ レポートファイルを保存
  └─ サマリーを表示
  ↓
[完了]
```

## ワークフローのベストプラクティス

### 1. 段階的な処理
各ステップを順番に実行し、前のステップの結果を次のステップに活用する。

### 2. エラーの早期検出
ステップ1で問題を検出し、可能な限り早い段階でユーザーに通知する。

### 3. 柔軟な対応
理想的な条件が満たされない場合でも、可能な範囲でレビューを継続する。

### 4. 透明性
各ステップで何を行っているかをユーザーに明示する。

### 5. 建設的なフィードバック
批判だけでなく、具体的な改善案を提示する。
