# Issue 作成判断基準

plan から Issue を作成する際の判断基準と手順。

## Issue 作成が必要なケース

### 必須ケース

| ケース | 理由 |
|--------|------|
| 新機能追加 | 仕様を記録し、将来の参照に備える |
| 既存機能の変更 | As-Is/To-Be を明確にする |
| 機能削除 | 削除理由と影響範囲を記録 |
| 破壊的変更 | 移行計画と影響を文書化 |

### 推奨ケース

| ケース | 理由 |
|--------|------|
| 複数選択肢の検討 | 判断経緯を記録 |
| ステークホルダー承認 | 合意形成の記録 |
| 複雑なバグ修正 | 根本原因と対策を文書化 |

### 不要なケース

| ケース | 理由 |
|--------|------|
| 単純なバグ修正 | PR で十分 |
| リファクタリング | 動作変更なし |
| ドキュメント更新 | PR で十分 |

## plan から Issue への変換

### 抽出する情報

| plan の要素 | Issue の項目 |
|-------------|-------------|
| 目的/背景 | 概要 |
| 現状の問題 | 現状 (As-Is) |
| 目標状態 | 変更後 (To-Be) |
| 検討した方法 | 検討した選択肢 |
| 採用理由 | 選択理由 |
| 懸念点 | トレードオフ・リスク |
| 完了条件 | 受け入れ条件 |
| 実装ステップ | タスク |

### 変換例

**plan 内容**:
```
## 目的
ユーザーがダークモードを使えるようにする

## 現状
- ライトモードのみ
- ユーザーから要望あり

## 方針
- CSS変数でテーマを管理
- localStorage で設定を保持
- システム設定を初期値に

## 懸念
- 既存コンポーネントの修正範囲が大きい

## ステップ
1. テーマ Context 作成
2. CSS変数定義
3. トグルボタン実装
```

**Issue 変換後**:
```markdown
## 種類
feat

## 概要
ユーザーがダークモードを使えるようにする

## 現状 (As-Is)
- ライトモードのみ対応
- ユーザーから複数の要望あり

## 変更後 (To-Be)
- ダークモード/ライトモードを切り替え可能
- 設定は localStorage に保持
- 初期値はシステム設定に従う

## 検討した選択肢
### 選択肢A: CSS変数によるテーマ管理 (採用)
- CSS変数でカラーを一元管理
- メリット: 変更が容易、パフォーマンス良好

### 選択肢B: CSS-in-JS のテーマ機能
- styled-components 等のテーマ機能を使用
- 却下理由: 既存コードが CSS Modules のため移行コスト大

## 選択理由
- 既存の CSS Modules との相性が良い
- 追加ライブラリ不要
- パフォーマンスへの影響が少ない

## トレードオフ・リスク
- 既存コンポーネントの CSS 修正が必要 (約30ファイル)
- IE11 非対応 (CSS変数のため)

## 受け入れ条件
- [ ] ダークモード/ライトモードの切り替えができる
- [ ] 設定がブラウザリロード後も保持される
- [ ] システム設定に応じた初期テーマが適用される

## タスク
- [ ] ThemeContext の作成
- [ ] CSS変数の定義
- [ ] トグルボタンコンポーネントの実装
- [ ] 既存コンポーネントの CSS 修正
- [ ] テスト追加
```

## 情報が不足している場合

以下を質問:

1. **As-Is が不明**: 「現在どのような状態/動作ですか?」
2. **To-Be が不明**: 「どのような状態にしたいですか?」
3. **選択肢が不明**: 「他に検討した方法はありますか?」
4. **受け入れ条件が不明**: 「何ができれば完了ですか?」
