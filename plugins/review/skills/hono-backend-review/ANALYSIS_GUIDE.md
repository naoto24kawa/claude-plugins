# トレードオフ分析ガイド

このガイドは、6つのレビューエージェントから得られた提案を統合し、相反する推奨事項のバランスを取るための分析手法を提供します。

---

## トレードオフパターン

### パターン 1: DDD厳格性 vs 実装シンプルさ

| 観点 | DDD厳格 | シンプル | 推奨 |
|------|---------|----------|------|
| 集約設計 | 完全なDDD集約 | 単純なCRUD | 核心ドメインはDDD、補助はCRUD |
| Value Object | すべてVO化 | プリミティブ許容 | ビジネスルールがあればVO |
| Repository | 完全抽象化 | 直接DB操作 | 書き込みはRepository、読み込みは直接可 |

**判定基準**:
- ビジネスルールが複雑 → DDD厳格
- 単純なCRUD → シンプル
- 将来の変更が予測される → DDD厳格
- プロトタイプ段階 → シンプル

```typescript
// DDD厳格: 核心ドメイン
class Order {
  private constructor(
    readonly id: OrderId,
    private items: OrderItem[],
    private status: OrderStatus
  ) {}

  static create(command: CreateOrderCommand): Order {
    // ビジネスルールを含む
  }
}

// シンプル: 補助ドメイン
const getSettings = (db: D1Database, userId: string) =>
  db.prepare("SELECT * FROM settings WHERE user_id = ?").bind(userId).first();
```

### パターン 2: イベント駆動 vs 同期処理

| 観点 | イベント駆動 | 同期処理 | 推奨 |
|------|-------------|----------|------|
| 整合性 | 結果整合性 | 即座の一貫性 | ユースケースで判断 |
| 複雑度 | 高い | 低い | 重要なイベントのみ非同期 |
| スケーラビリティ | 高い | 制限あり | 負荷特性で判断 |

**判定基準**:
- Context間通信 → イベント駆動
- 単一Context内 → 同期処理可
- 高スループット要件 → イベント駆動
- 即座の確認が必要 → 同期処理

```typescript
// イベント駆動: Context間
await eventPublisher.publish({
  type: "order.placed",
  orderId: order.id.value,
});

// 同期処理: Context内
const items = await orderItemRepository.findByOrderId(order.id);
```

### パターン 3: マイクロサービス分割 vs モノリス保守性

| 観点 | マイクロサービス | モノリス | 推奨 |
|------|-----------------|----------|------|
| デプロイ | 独立 | 一括 | モジュラーモノリスから開始 |
| 運用 | 複雑 | シンプル | チーム規模で判断 |
| 整合性 | 結果整合性 | ACID | ドメイン要件で判断 |

**判定基準**:
- チーム3名以下 → モノリス
- 明確なContext境界あり → マイクロサービス候補
- スケーリング要件が異なる → マイクロサービス
- 独立したリリースサイクル → マイクロサービス

---

### パターン 4: 型厳格性 vs 開発速度

| 観点 | 型厳格 | 開発速度 | 推奨 |
|------|--------|----------|------|
| 公開API | 必須 | - | 厳格な型定義 |
| 内部実装 | 推奨 | 許容 | 適度な型定義 |
| プロトタイプ | - | 優先 | 緩め、後で厳格化 |

**判定基準**:
- 公開API → 型厳格必須
- 型エラーがバグにつながった → 厳格化
- 新規開発 → 最初から厳格に
- レガシー移行 → 段階的に厳格化

## 優先度判定基準

### Critical（即時対応）

1. **セキュリティ**
   - 認証・認可の不備
   - シークレットの露出
   - インジェクション脆弱性

2. **データ整合性**
   - トランザクション不整合
   - 競合状態によるバグ

3. **Cloudflare制約違反**
   - CPU時間超過
   - メモリ制限超過

### High（優先的に対応）

1. **保守性への大きな影響**
   - Context境界の曖昧さ
   - 循環依存

2. **信頼性リスク**
   - 冪等性の欠如
   - リトライ戦略の不在

3. **パフォーマンス問題**
   - N+1クエリ
   - 非効率なKV/D1使用

### Medium（計画的に対応）

1. **コード品質**
   - 型定義の不足
   - 命名の改善

2. **設計改善**
   - DDDパターンの適用
   - イベント設計の改善

### Low（将来的な改善）

1. **最適化**
   - キャッシュ戦略
   - Cold Start対策

2. **ベストプラクティス**
   - ドキュメント整備
   - テストカバレッジ向上

## 意思決定フレームワーク

### デシジョンツリー

```
提案が相反する
├─ セキュリティに関わる？
│   └─ Yes → セキュリティ優先
│
├─ Cloudflare制約に関わる？
│   └─ Yes → 制約対応優先
│
├─ データ整合性に関わる？
│   └─ Yes → 整合性優先
│
├─ 実装コストは？
│   ├─ 高い → シンプルな方を選択
│   └─ 低い → より良い設計を選択
│
└─ チームの習熟度は？
    ├─ 低い → シンプルで理解しやすい方
    └─ 高い → より高度な設計
```

---

## まとめ

1. **セキュリティと制約を最優先**
2. **実装コストと効果のバランスを考慮**
3. **段階的アプローチでリスクを最小化**
4. **チームの現実を無視しない**
5. **完璧を求めず、継続的改善を目指す**
