# React レビュー トレードオフ分析ガイド

このガイドは、複数のエージェントからの相反する提案を統合し、最適な改善計画を策定するための手法を定義します。

## トレードオフパターン

### 1. コンポーネント分割 vs KISS（シンプルさ）

| 観点 | コンポーネント分割推奨 | KISS推奨 |
|------|------------------------|----------|
| 状況 | 再利用性が高い、責任が複数 | 一度しか使わない、単純なUI |
| 判断基準 | 150行超、Props10個超 | 100行以下、Props5個以下 |
| 優先 | 保守性・再利用性重視 | 開発速度・可読性重視 |

**調整方法**: 再利用の可能性と現在の複雑さで判断。将来的な再利用が見込めない場合はKISSを優先。

### 2. メモ化 vs 可読性

| 観点 | メモ化推奨 | メモ化不要 |
|------|-----------|-----------|
| 状況 | 高頻度更新、重い計算 | 低頻度更新、軽い処理 |
| 判断基準 | 親の更新頻度が高い、計算コスト高 | 更新頻度が低い |
| リスク | 過剰なメモ化で可読性低下 | パフォーマンス問題 |

**調整方法**: 実測データに基づいて判断。問題が発生してからメモ化を追加するのも有効。

### 3. 状態管理の集中 vs 分散

| 観点 | 集中（Context/useReducer） | 分散（ローカルstate） |
|------|---------------------------|---------------------|
| 状況 | 複数コンポーネントで共有 | 単一コンポーネント内 |
| 判断基準 | 3階層以上のProps伝播 | 2階層以下 |
| リスク | 不要な再レンダリング | Props Drilling |

**調整方法**: 共有の必要性で判断。将来的な共有可能性よりも現在の必要性を優先。

### 4. アクセシビリティ vs 開発速度

| 観点 | a11y優先 | 開発速度優先 |
|------|---------|-------------|
| 状況 | 公開サービス、法的要件 | 内部ツール、MVP |
| 判断基準 | WCAG AA必須 | 基本的なキーボード操作のみ |
| リスク | 開発時間増加 | ユーザー排除 |

**調整方法**: 基本的なa11y（キーボード操作、セマンティックHTML）は常に必須。高度な対応はフェーズ分け。

### 5. テスト容易性 vs 実装コスト

| 観点 | テスト容易性優先 | 実装速度優先 |
|------|-----------------|-------------|
| 状況 | 長期運用、複雑なロジック | 短期プロジェクト、単純なUI |
| 判断基準 | ビジネスロジックの複雑さ | 単純な表示のみ |
| リスク | 過剰な抽象化 | テスト困難なコード |

**調整方法**: ビジネスロジックのみカスタムフック抽出。UIのみのコンポーネントは簡素に保つ。

## 優先度判定マトリクス

### Critical（即時対応）

- セキュリティリスクがある
- アクセシビリティの致命的な問題（操作不能）
- 本番環境でのパフォーマンス問題（体感できるレベル）

### High（今Sprint内）

- アクセシビリティの重要な問題
- 状態管理の設計ミス（バグの温床）
- 再レンダリングの明らかな無駄

### Medium（次Sprint）

- コンポーネント設計の改善
- テスト容易性の向上
- shadcn/uiベストプラクティスへの準拠

### Low（バックログ）

- 細かいコードスタイル
- 軽微なパフォーマンス改善
- ドキュメント追加

## 相反する提案の調整

### 複数エージェントの提案が矛盾する場合

1. **優先度で判断**: アクセシビリティ > パフォーマンス > 保守性 > コード美観
2. **実測データで判断**: パフォーマンス関連は計測結果を優先
3. **チーム方針で判断**: 既存のコーディング規約を尊重
4. **段階的に対応**: 両方を満たす中間解を検討

### 調整の例

**Component Design vs Performance**:
- 「コンポーネントを分割すべき」vs「メモ化で対応すべき」
- → 再利用性があれば分割、なければメモ化で対応

**State Management vs Testability**:
- 「Contextで状態共有」vs「依存性注入でテスト可能に」
- → Contextを使いつつ、Provider経由で依存性注入可能にする

**Accessibility vs Performance**:
- 「aria-live設定」vs「頻繁な更新を避ける」
- → aria-live="polite" で控えめに通知、debounceで更新頻度を制御
