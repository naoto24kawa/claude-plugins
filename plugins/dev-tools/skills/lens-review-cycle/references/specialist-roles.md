# Specialist Roles

5〜7 のレンズ（ロール）の定義とプロンプトテンプレート。既定ではレビュアー 1 名がこれらを順に当てる（SKILL.md「実行モデル」）。テンプレートは「1 レンズ分の指示」であり、1 名に渡すときはレンズごとの節として連結する。

**全テンプレート共通の報告規定**（テンプレの「報告フォーマット」に必ず併記する）: `references/agent-output-principles.md`（同スキル内）の scope フィルタに従い、**`[ISSUE]` は flag（correctness・セキュリティ・明示要件に影響）のみ**。optional（それ以外）は `[ISSUE]` 形式で書かず「LGTM／optional: <概要>」と併記する。サイクル継続判定は `[ISSUE]` のみカウントする。

レビュアーには `Write` ツールを渡し、オーケストレータがレンズごとに解決した絶対パス `{findings_path}` だけへ完全な findings を書かせる（1 名がレンズの数だけファイルを書く）。パスの role 部分は `security` / `core-logic` / `tests` / `domain` / `fresh-eyes` / `ambiguity-hunter` / `altitude-checker` のいずれかを使う。findings ファイルの先頭行には `LGTM`、`LGTM／optional: ...`、または `flag N件` の結論を必ず書き、その後に全内容を残す。応答本文は同じ結論と書き込んだパスだけとするが、有効性判定には使わない。オーケストレータはファイルから集約する。

## ロール一覧

### #1 Security（セキュリティ専門）

**フォーカスエリア:**
- 注入攻撃（SQL インジェクション、コマンドインジェクション、CRLF インジェクション）
- パストラバーサル（`../` や symlink バイパス）
- 認証・認可の不備
- 情報漏洩（エラーメッセージへの機密情報露出）
- 入力サニタイズの漏れ

**プロンプトテンプレート:**
```
あなたは {project} の**セキュリティ専門**レビュアーです。確信度 80% 以上の問題のみ報告してください。

## レビュー対象ファイル
{file_list}

{fixed_items}

## 設計上の事実
{design_facts}

## 既知の偽陽性
{fp_registry_contents}

## フォーカス
- 注入・パストラバーサル・情報漏洩リスク
- 入力サニタイズの適用漏れ

## 報告フォーマット
```

### #4 Domain（ドメイン専門）

ドメイン専門ロールはプロジェクトの性質に合わせてカスタマイズする。

**典型的な例:**

| プロジェクト種別 | フォーカスエリア |
|---|---|
| CLI ツール | エラーハンドリング・UX・exit コード・リソースリーク |
| REST API | ステータスコード・バリデーション・べき等性・レート制限 |
| DB 層 | マイグレーション安全性・インデックス・デッドロック |
| フロントエンド | アクセシビリティ・パフォーマンス・XSS |
| MCP サーバー | ツール定義の正確性・エラー伝播・stdio 安全性 |
| 顧客向け成果物・PoC | 顧客価値・本番化可能性（セキュリティ/ガバナンス/運用）・「使われるか」 |

**カスタム agent をロールとして使う**: 対象が顧客向け成果物・PoC の場合、Claude Code 環境で `fde` エージェントが定義されている場合に限り、プロンプトテンプレートの代わりに `Agent` ツールの `subagent_type: fde` で FDE エージェントをそのままディスパッチしてよい（未定義の環境では通常のプロンプトテンプレートを使う）。その際もレビュー対象ファイル・修正済み事項・設計上の事実・FP レジストリの内容・報告フォーマット（LGTM / [ISSUE] 形式・確信度80%以上）はプロンプトで必ず渡すこと（fde 側は呼び出し元の報告フォーマット指定を既定出力より優先する規定を持つ）。また、プロンプト冒頭で「FDE観点（顧客価値・本番化可能性）でのレビュー依頼」であることを明示すること（fde はレビュー目的での利用を FDE観点の明示依頼時に限定しているため）。

### #5 Fresh Eyes（フレッシュアイ）

**フォーカスエリア:**
- 先入観なしの総合チェック
- 他のスペシャリストが見落とした横断的な問題
- コードの可読性・保守性
- 過剰実装（YAGNI・早すぎる抽象化・不要なレイヤー / 設定項目 / 間接参照）。他レンズは「足りない・間違っている」を見るため、**削除方向を担当するのはこのロールのみ**。flag にするのは降格理由の欠落のみ（判定条件は `references/agent-output-principles.md` の scope フィルタが正本）
- 設計上の事実として与えられた内容の妥当性検証

**重要:** Fresh Eyes は「設計上の事実」を受け取るが、それを鵜呑みにせず独立して評価する。「修正済み事項」は**受け取らない**（下記注意参照）。ただし FP レジストリは尊重する（レジストリは「すでに検証された偽陽性」のリスト）。

**プロンプトテンプレート:**
```
あなたは {project} の**フレッシュアイ**レビュアーです。先入観なくコードを読み、確信度 80% 以上の問題のみ報告してください。

## レビュー対象ファイル（全て読んでください）
{file_list}

## 既知の設計判断（偽陽性を避けるための情報）
{design_facts}

## 既知の偽陽性（これらは報告不要）
{fp_registry_contents}

## フォーカス
- 他レンズが見落とした横断的な問題・可読性・保守性
- 過剰実装（YAGNI・早すぎる抽象化・不要なレイヤー / 設定項目 / 間接参照）。他レンズは「足りない・間違っている」を見るため、**削除方向を報告するのはあなただけ**
- ただし flag にするのは「インフラ・標準機能・既存ライブラリで足りるのに自前実装へ降りていて、その降格理由が成果物に無い」場合のみ。「もっとシンプルにできる」という主観的な簡素化案は optional で報告する

## 報告フォーマット
問題がなければ「LGTM」と一言。問題がある場合のみ:
[ISSUE] ファイル名:行番号
確信度: X%
問題:
修正案:
```

**注意:** Fresh Eyes には「修正済み事項」を明示しない。修正済みのはずの問題が再浮上する場合、修正が不完全な可能性があるため。

## カスタマイズガイド

### ロールの増減

- **指摘が少ない場合**: Tests と Domain を統合し、Fresh Eyes を別ラウンドで当て直すと盲点発見に有効
- **指摘が多い場合**: Domain ロールを 2 つに分割（例: CLI + Server を別ロールに）
- **偽陽性が多い場合**: 各ロールの「設計上の事実」セクションを充実させる

### 対象ファイルの割り振り

全ロールに同じファイルリストを渡してよい（専門性がフォーカスを絞る）。
ただしファイル数が多い場合は:
- Security/Fresh Eyes: 全ファイル
- Core Logic: コアロジックのみ
- Tests: テストファイルのみ
- Domain: CLI/API/DB など対象層のみ
